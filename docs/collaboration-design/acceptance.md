# QuanDeck 协作后端：不变量与验收场景

本文件是**待实现、待执行的产品验收规范**。下述场景均为未来验收，不表示 QuanDeck 当前版本已通过。本次设计交付的文件语法、SQL 建表或 JSON 结构检查，应单独记录，不得替代真实后端、真实运行器与人工端到端验收。

## 1. 范围与统一词义

- 纳管范围：QuanDeck 创建、导入、接入或人工登记的工作；未接入工具中的未知工作不计入“全部任务”覆盖率。
- `Task` 是稳定的交付目标；`Run` 是一次 AI 执行；`Session` 是对话容器或运行器的外部会话；`ArtifactVersion` 是不可静默覆写的成果版本。
- 任务负责人 `owner` 对交付负责；`executor` 是本次执行者，两者可不同。人工任务无需伪造 AI run、session 或 token。
- Task 状态固定为 `draft | ready | running | blocked | paused | in_review | done | failed | cancelled`。
- Run 状态固定为 `queued | running | waiting_input | waiting_permission | paused | succeeded | failed | cancelled | lost`。
- 新协议的 Task `done` 表示指定任务版本按指定验收规则已被接受。迁入的旧版完成记录可以标为 `legacy_import` 并保留原证据，但不得补造新协议验收，默认不能满足要求新协议验收的依赖。Run `succeeded` 只表示本次运行结束且结果满足运行协议，不自动等于 Task `done`。
- 资料有效性与任务完成状态分开。旧成果过期不抹掉“当时完成过”的历史；应标记资料待复核，并生成复核提案或显式开启新的任务版本。
- 命令名称、字段名称最终以随附协议及数据库映射为准；本文对行为、断言和故障点的要求不因命名变化而改变。

## 2. 必须成立的不变量

| ID | 不变量 | 由谁强制 |
|---|---|---|
| INV-01 | 所有可执行任务具有稳定 ID、所属项目、负责人、当前版本、目标、验收条件；缺少影响执行的条件时不能冒充 ready。 | 后端命令处理器 |
| INV-02 | 一个 run 固定绑定一个 task 版本、输入上下文快照和执行者；恢复、重试创建可区分的新 run，不改旧 run 的归属。人工无 run 合法。 | 数据模型与业务校验 |
| INV-03 | 台帐是权威结构化记录的查询视图；黑板中的负责人、状态、依赖、阻塞与下一步由同一记录派生。AI 描述不能成为第二套权威状态。 | 查询层与投影器 |
| INV-04 | 每次有效变更在同一事务中写入业务状态、版本、审计事件及必要 outbox；没有事件的成功状态或没有状态的“成功回执”都不允许。 | 事务边界 |
| INV-05 | 写命令同时核验身份、项目范围、操作权限、预期版本、状态转换和幂等键；AI 提供的 actor、审批或租约声明不能自证有效。 | 认证与命令处理器 |
| INV-06 | 同一任务未经显式拆分/分工，仅有一个可提交当前结果的执行权。接管令 fencing token 递增；旧 token 的回报不得推进当前状态。 | 领取事务与结果入口 |
| INV-07 | agent 租约失效表示需要核对/接管，不证明进程或外部副作用已经停止。人工负责人不因缺少机器心跳被自动替换。 | 调度器与运行器适配器 |
| INV-08 | 用户确认条件、验收规则和授权只能由有权主体通过明确变更命令建立新版本。AI 假设、旧对话和外部材料不能覆盖它们。 | 命令权限与版本规则 |
| INV-09 | AI 可提交计划提案、成果、证据和完成建议；完成验收只能由获授权的人或已授权的验收规则决定，不能由同一段“我完成了”的自由文本决定。 | 验收服务 |
| INV-10 | 已提交/采纳的成果正文、证据指针、输入快照和事件不得原地改写；纠错创建新版本或更正事件。当前有效指针可以通过合法命令更新。 | 存储与业务校验 |
| INV-11 | 每个上下文包固定来源版本，包含已确认的关键约束、缺口和来源指针；预算不足不能静默删掉硬约束。 | 上下文装配器 |
| INV-12 | 检索先按身份与项目权限限制候选，再排序；未获授权材料不能经摘要、搜索计数、向量结果或引用间接泄漏。 | 数据查询与检索层 |
| INV-13 | 下一步建议不等于任务已授权执行。依赖、预算、权限与停止条件全部满足，代码才能派发。 | 调度器 |
| INV-14 | 外部副作用通过可审计执行记录管理；结果未知时先核对。outbox 可以重复投递，消费者必须去重；不得声称任意外部系统天然 exactly-once。 | 工具网关与 outbox 消费者 |
| INV-15 | 总成本覆盖所有实际调用并防止父子重复归集；缺失用量为 unknown，不能伪造为零。预算计算与领取/派发关联。 | 计量与预算服务 |
| INV-16 | 常规业务不可覆盖历史，不代表永远不能删除个人数据。删除/脱敏需独立授权流程，连同附件、索引、缓存、导出与备份策略处理。 | 数据生命周期服务 |

### 2.1 状态语义约束

- `ready`：本次执行必要条件已满足，且可由调度规则选择；仍需在真正派发前再次核验动态条件。
- `running`：工作正在进行；`blocked`：缺少信息、权限、依赖或决策，必须有明确原因与解除条件。
- `paused`：明确暂停；`failed`：当前目标尚未完成且此次处理失败；不能以“失败”替代所有等待状态。
- `in_review`：已有提交，等待验收；规则自动验收也应留下验收证据和状态转换记录。
- `done`、`cancelled` 不因运行器的新消息自动重开；需要合法的新任务版本/重开命令。
- 请求取消与已确认取消分开记录：请求发送后，运行器尚未确认停止时，不得伪称外部动作已停止。
- 等待用户输入、等待权限与暂停均不得忙循环反复调用模型。
- 已完成父任务必须满足其验收规则与所需子任务/依赖条件，不能仅因父会话结束而完成。

## 4. 二十个产品验收场景

### A01 首次创建项目、台帐与黑板

**Given**：空数据库，无 AI 连接，无任何模型额度。

**When**：U1 创建项目 P1，并立即打开台帐与黑板；重复打开 3 次。

**Then**：
1. 项目、初始项目版本和创建事件存在且归属 U1。
2. 台帐和黑板可正常返回空任务视图，并包含可核对的项目版本/事件水位。
3. 不创建示例任务、不伪造 AI run、不调用模型；3 次读取不新增业务事件或重复项目。
4. 页面能区分“没有任务”与“数据加载失败”。
5. 黑板摘要可为空；缺少 AI 摘要不影响结构化状态可用。

### A02 黑板不是第二套数据库，预览不提交

**Given**：T83 的负责人为 U1，版本为 1；台帐和黑板显示同一状态。

**When**：
1. AI 建议改负责人并新增下一步，用户只查看预览后关闭。
2. 用户随后明确采纳其中一项合法变更。
3. 让黑板异步投影暂时延迟。

**Then**：
1. 关闭预览不改变任务、负责人、依赖或当前计划；提案可以作为草稿保留。
2. 采纳产生一次受版本检查的业务命令、一个新版本和相应事件；不能先改黑板再异步猜测台帐状态。
3. 延迟时黑板标明当前水位/待刷新，不能把旧投影标成最新状态。
4. 重建投影后，黑板与台帐一致；重复重建不重复写业务记录。
5. 如支持手工黑板备注，备注与任务事实明确分开，不能覆盖结构化负责人或状态。

### A03 任务、执行与会话身份稳定

**Given**：T83@v1 的运行 R1 使用 S1，已有检查点和成果草稿。

**When**：R1 需要更换会话或重试，创建 R2/S2；之后产生独立交付目标“核验铁路时刻”。

**Then**：
1. R2 仍属于 T83，引用新的上下文快照，并保留来自 R1 的检查点关系。
2. R1 的 task、输入快照和历史会话归属未被修改；S1 的原记录仍可追溯。
3. “核验铁路时刻”创建新的子任务 ID，与 T83 建立明确依赖或父子关系。
4. 查询 T83 显示 1 个任务、2 次执行，不误计成 2 个完成任务。
5. 如新窗口实际仍接收全历史，实际模型输入检查必须揭示这一事实，不能仅以 UI 窗口数量通过验收。
6. 供应商尚未返回源会话 ID 时，内部 session 可处于待映射阶段，source_session_id 为空；不得用本地 task/session ID 伪造供应商身份。收到真实受理回执后才补充映射，已发出的上下文快照不原地修改。

### A04 人工任务无需 AI，能够参与同一工作流

**Given**：AI 研究任务已验收，人工任务 H1“选择住宿”依赖它；AI 汇总任务 T83 依赖 H1。

**When**：U1 领取 H1、提交选择说明及附件；由有权主体验收 H1；随后启动 T83。

**Then**：
1. H1 无需 run/session，AI token 计为不适用，人工投入单独记录。
2. H1 提交后进入 in_review，未验收前 T83 不得因“上传过附件”自行 ready/派发。
3. H1 验收后，代码重新计算 T83 的依赖与权限；只有全部满足才进入可执行状态。
4. 整条链可定位研究成果、人工选择原话、验收者和后续输入快照。
5. U1 离线或不发送心跳，不导致 H1 被自动改派给 AI。

### A05 并发领取与命令幂等

**Given**：T83 ready、version=1，无有效执行权。

**When**：AI-A、AI-B 同时携带 expected_version=1 领取；再对成功请求以同一幂等键重发 3 次。

**Then**：
1. 仅一个领取成功；另一请求得到可区分的版本冲突或任务已被领取结果。
2. 只创建一个有效执行权、一个对应 run、一次有效派发 outbox 项。
3. 同幂等键同内容重发返回同一个已保存结果，不新建 run。
4. 同幂等键但不同内容必须拒绝，不能误返回旧请求的成功或接受新副作用。
5. 单独拒绝请求可以记录审计，但不递增成功业务版本。

### A06 租约失效、接管与迟到结果

**Given**：R1 拥有 fencing token=7；后端时间推进使其租约失效，运行器是否停止尚不确定。

**When**：核对并合法接管后，R2 获 token=8；随后 R1 以 token=7 提交成果、心跳和派发下一步请求。

**Then**：
1. R1 不得恢复当前执行权，不得更新当前任务状态或成果当前指针。
2. 迟到内容可作为被隔离的运行观察记录保留，明确“不被当前任务采纳”。
3. 所有写入口和受管工具入口均检查 fencing token，不能只在心跳接口检查。
4. 若旧运行可能仍在执行外部动作，相关任务保持阻塞/待核对，不能盲目启动重复动作。
5. 接管事件保留操作者、原因及新旧执行权，且人工 owner 不被心跳机制自动替换。

### A07 等待、暂停、取消与进程恢复

**Given**：R1 正在运行，能够返回 waiting_input、waiting_permission 和取消确认等运行事件。

**When**：
1. 分别触发缺信息、缺权限、明确暂停。
2. 在等待期间模拟 10 次调度 tick。
3. 请求取消，但延迟运行器的停止确认。
4. 关闭应用再重启。

**Then**：
1. 等待原因与解除条件可见；task/run 使用规定枚举，不以 failed 代替正常等待。
2. 10 次 tick 不反复调用模型、不重复请求同一权限、不丢失已有输入。
3. 用户回复或批准后，只恢复对应 task/run，不误恢复其他项目任务。
4. 取消请求和停止确认分别可查；确认前不显示“外部执行已停止”。
5. 重启先与运行器核对；不可恢复的连接标为 lost/待处理，不伪造 succeeded。
6. 存在结果不确定的外部动作时，走 A15 的核对流程。

### A08 回收 AI 结果不自动完成任务

**Given**：T83 running；验收条件要求保留 C1、C2，并提供实际成果及来源。

**When**：
1. AI 只回复“完成了”。
2. AI 提交格式正确但缺少来源的结果。
3. AI 提交符合协议的完整结果。
4. 分别执行拒绝验收和通过验收。

**Then**：
1. 自由文本不能直接修改 task.status=done，也不能仅凭外部进程 exit=0 判定业务完成。
2. 格式/引用不合格的结果返回具体校验错误，并保留必要诊断；不伪造验收成功。
3. 完整结果被持久化后进入 in_review；run 可按协议结束，但 task 尚未 done。
4. 拒绝产生验收记录及返工路径；通过产生接受记录、被接受成果版本和 task.done 转换。
5. 自动验收仅使用事先获授权的规则；规则版本、检查证据和触发者均可查。
6. 同一个完成回报重复回收 3 次，不重复生成已采纳成果或下游任务。
7. 若使用 AI 复核，创建独立复核任务及 purpose=review 的运行，引用原提交和验收规则版本；不得抢占产出任务的主执行权。复核输出是 advisory，仍需合法验收命令。
8. 合法提交已经落盘后，即使生产 run 正常结束或原租约到期，验收仍可进行；核验提交时执行权有效、当前要求与证据仍适用，而非要求生产 agent 永久在线。

### A09 用户已确认条件、授权与并发变更

**Given**：用户已确认 C1、C2，任务版本 1 的 run 已启动。

**When**：
1. AI 推断用户“应该可以多走路”，尝试覆盖 C1。
2. 用户通过明确命令修改 C2，建立新的条件版本。
3. 旧 run 携带旧任务版本提交结果。
4. AI 尝试自报“用户已批准预订”。

**Then**：
1. AI 只能提交条件变更建议或假设；C1 当前有效值不变。
2. 用户原确认和新确认都可查，当前指针按授权命令更新。
3. 旧输入版本可定位；受变化影响的结果进入冲突/待复核流程，不能无提示成为当前采纳版本。
4. 采用新条件需要确定性版本检查；不能以模型摘要声称“已同步”。
5. 自报批准不创建授权，必须关联可信的批准记录、对象版本和范围。
6. 仅更新不影响当前执行的备注，不应无理由地中止所有运行；影响判定规则必须有记录。

### A10 成果版本、旧引用与纠错

**Given**：A5@v2 已被 T83 的上下文引用，用户在其中一段留下批注；A5@v3 修正了一个错误。

**When**：采纳 A5@v3；打开旧 T83 记录、旧批注和当前搜索结果。

**Then**：
1. A5@v2 内容与 hash 不变，旧引用仍定位 v2，不静默跳到 v3。
2. 当前有效成果指针指向 v3，并保留“更正/取代 v2”的关系与原因。
3. 批注锚点失效时保留旧引用快照，不能丢弃或移到无关段落。
4. 默认检索优先当前有效版本；历史查询可以显式看到被取代版本及其状态。
5. 已经在旧版本上完成的任务仍保留其验收历史；需要复核时建立明确的复核关系。

### A11 冷启动接力与关键约束保留

**Given**：准备至少 20 个有人工标注的代表性任务；每项标出目标、关键条件、否决项、已完成事项、下一步和正确证据位置。

**When**：为每项启动完全新会话；只提供交接包与受控检索工具，初始输入不带完整旧对话；允许按需展开证据。

**Then**：
1. 所有标为关键的条件均在交接包内或有必须加载且成功加载的确定性引用；未加载不能直接执行。
2. 新会话能正确重述目标、关键约束、已完成和下一步；逐项评分，不以文风评价替代。
3. 存在冲突时提出具体缺口，不能自行补出预算、日期、权限或用户选择。
4. 实际输入、追加检索、引用版本与遗漏项都有记录。
5. 发布门槛：测试集关键约束遗漏为 0；不满足时阻止该类任务自动续做，并修复装配/检索策略后重测。
6. 该门槛是测试集标准，不宣称任何模型在所有未来任务上永不遗漏。

### A12 历史规模从 100 增至 1000

**Given**：固定 T83、同一组用户条件、相同相关证据版本和同一 token 计数方式；分别放入 100 条与 1000 条无关历史任务。

**When**：生成同一个初始上下文包，并执行相同检索查询。

**Then**：
1. 启动输入不含全量台帐或全部历史会话，相关证据与关键条件保持完整。
2. 两次均不超过配置预算；建议首轮门槛为启动输入 token 增幅不超过 10%，以后按实测调整并版本化。
3. 预算不足返回明确原因或进一步拆分/检索策略；不能截断硬约束后照常派发。
4. 记录检索延迟、候选数、追加展开次数；不得把省下的输入成本隐藏为无限检索调用。
5. 可在无 AI 服务情况下生成结构化索引与基础黑板，证明项目规模不会强制触发全量 AI 总结。

### A13 过期资料、相互矛盾与被否决方案

**Given**：A5 的班次已过核验期限；C10 是清迈住宿，E21 是曼谷当日游；用户曾明确否决某住宿区域。

**When**：系统为 T83 检索并装配资料，AI 提交整合方案。

**Then**：
1. 适用范围、来源和核验时间进入候选评价，不能仅按文字相似度直接拼接。
2. 确定性可识别的过期/城市/日期冲突在派发前标记；语义冲突由 AI 提议并保留证据，不能假装代码能证明一切旅行事实。
3. 需要确认的信息明确进入待核验清单；必要时创建核验提案/子任务。
4. 已否决方案不会重新作为默认选项，无新的用户确认不得撤销否决。
5. 变更出行日期后，沿成果依赖关系标记受影响资料；无关的通用介绍不必全部重新研究。

### A14 依赖、下一步与授权停止条件

**Given**：任务图已有 A→B；项目只授权研究工作，预算剩余有限，未授权订票。

**When**：
1. 提案新增 B→A 的依赖环；另测把祖先任务设置为自己的子任务所形成的父子层级环。
2. AI 提议订票并写“现在开始”。
3. 同一 AI 连续提交重复的下一步建议。
4. 项目完成或预算触顶后再次触发调度。

**Then**：
1. 形成环的依赖命令与父子层级修改都被拒绝，原图不受部分更新；不能只检查直接指向自己的单节点环。
2. 订票可留作待决策提案，但不会创建有权执行的外部动作。
3. 相同来源提案/幂等键不会无限生成相同任务；相似但不同提案需显式关联与合并决策。
4. 调度时重新核验依赖、授权、容量、预算和停止条件。
5. 完成或停止后的项目不自动扩张范围；下一步为空必须能解释为结束、等待或阻塞。
6. 人工日程容量不足时产生可解释的排期结果，不将 AI 无限并行假设套到人工。
7. 用户仅要求讨论方法时，规划本身使用独立规划任务及 purpose=discussion 的运行，照常记录输入、费用和 plan_proposal；它不会自动启动计划内的执行子任务。不得为绕过严格协议而允许无 task/run/context 绑定的 AI 提案直接写权威数据。

### A15 外部副作用结果未知

**Given**：外部服务可能已经创建订单/发出消息，但响应丢失；另有服务不支持幂等也无法查询。

**When**：网络超时，运行器重启或任务接管后准备重试。

**Then**：
1. 外部操作记录区分未开始、执行中、成功、失败与结果未知；超时不能直接判为“未执行”。
2. 支持幂等时复用同一业务操作键，查询或重试不会产生第二个外部对象。
3. 支持查询时先根据外部回执/操作键核对；找到成功结果则回填，不再执行一次。
4. 既无幂等也无法核对时阻塞并要求有权主体处理，不盲目重发。
5. 系统不能声称单靠本地事务保证外部 exactly-once；无法控制的运行器直连路径应标出能力缺口。
6. 同一已授权动作的重试不扩大授权对象、金额或收件人范围。

### A16 事务、附件与 outbox 故障恢复

**Given**：一次结果提交包含成果正文、附件、状态变更和下游通知；投递可重复。

**When**：分别在以下位置终止进程：附件临时写入后、附件持久化后但 DB commit 前、DB commit 后但 outbox 发送前、消费者处理后但 ack 前。

**Then**：
1. commit 前失败不能留下已采纳状态；未关联附件进入可回收的暂存状态。
2. commit 成功的成果所引用附件必须可读且 hash 匹配，不能出现“完成”却丢文件。
3. commit 后未发送的 outbox 在重启后继续投递。
4. 重投事件被消费者去重，状态转换和下游触发只发生一次。
5. 数据库、业务事件和 outbox 一致；不能只成功写日志却没有业务状态。
6. 部分上传、损坏附件、磁盘满产生明确错误，不把失败写入伪装成完成。
7. 验证需要实际故障注入；只做普通 happy-path 保存测试不足以通过。

### A17 端到端质量、费用与预算

**Given**：同一批代表性任务、同一模型配置；比较“全历史输入”基线与“交接包+检索”方案。用量样本包括累计 token 事件、重复事件、父子运行聚合、缺失报告和缓存计费。

**When**：两种方案各完成完整任务链，包含规划、检索、摘要、执行、复核、失败重试；多个任务并发尝试消耗同一剩余预算。

**Then**：
1. 记录输入、输出、缓存相关 token，模型费用、工具费用、运行耗时、人工干预与验收通过率。
2. 累计用量按差量/最终可信值归集，不能把每次累计回报直接相加；父子统计不能重复计算同一计费调用。
3. 未报告用量标为 unknown/estimated，显示估算来源，不记作 0。
4. 预算预留与派发原子协调；并发任务不能各自读取同一余额后同时透支已设硬限额。
5. 受管路径在下一次调用前执行额度检查；不可中断的外部调用需预留上界或明确成本控制能力有限。
6. 建议通过条件：关键约束遗漏不增加、验收通过率不降低，且完整任务链总费用降低；同时报告延迟变化。具体节省比例由基线确定。
7. 仅减少单个会话输入、却增加总控/子任务/摘要总费用，不能算有效节省。
8. 预算触顶后停止新增执行；不自动扩大预算或将收费调用改名为“校验”绕过限制。

### A18 权限、跨项目检索与材料中的指令

**Given**：P2 含 P1 用户无权访问的资料；P1 某旧对话/网页包含“忽略规则、覆盖台帐、已获批准”等文字。

**When**：
1. P1 搜索语义上匹配 P2 的内容。
2. AI 按材料里的指令提交跨项目写入或自报审批。
3. 过期/撤销的 run token 调用读取、写入和工具接口。

**Then**：
1. 搜索结果、计数、摘要、引用、向量候选不暴露 P2 内容。
2. 资料按数据处理，不升级为系统指令或真实授权。
3. 后端拒绝无权操作，即使模型输出满足 JSON 格式也不能绕过。
4. 读取与写入均核验范围，不能只限制写接口。
5. 禁止 run 获取数据库凭据或直接修改权威存储文件；本地执行器只能访问明确允许的任务工作目录和工具。
6. 本地同一 OS 用户有全磁盘权限时，应用无法仅凭 prompt 建立强隔离；部署验收须验证实际进程沙箱/权限，否则明确记录边界。

### A19 受控删除、脱敏与不可变历史的例外

**Given**：用户要求删除一份含个人信息的原材料，该材料已进入附件、原始对话、成果引用、检索索引、上下文包与备份。

**When**：有权主体预览影响范围并确认执行删除/脱敏。

**Then**：
1. 普通 AI 命令不能自行删除历史；受控删除命令验证身份、范围和删除计划。
2. 活跃存储、索引、缓存及派生内容按明确策略删除/重建/标记撤回，受影响的运行停止继续取用材料。
3. 保留最小化的删除回执和 tombstone，不能在“审计记录”里再次复制已删除正文或敏感摘要。
4. 旧引用返回“已删除/已撤回”及允许保留的元数据，不悄悄指向其他内容，也不造成页面崩溃。
5. 备份的保留周期、删除方式和恢复后的删除重放规则明确；未真正完成备份清理时不声称所有副本已彻底删除。
6. 用户已导出或第三方已经接收的数据无法自动保证回收，应提供准确范围说明。
7. 法定保留或组织保留策略若适用，应明确具体依据与范围；不得用泛化“审计不可变”取消用户删除能力。

### A20 既有数据迁移、备份与恢复

**Given**：现有本地项目包含人工成果、多个会话换绑历史、附件与不完整旧用量；准备迁移前备份。

**When**：
1. 执行迁移，并在中途故障后重试。
2. 用恢复包在新目录恢复。
3. 在迁移/恢复后运行完整性检查与代表性任务读取。

**Then**：
1. 原 task ID、人工内容、附件 hash 和已知会话历史保留；不把旧换绑历史静默改写为新的确定性 run 归属。
2. 无法唯一识别的旧归属标为待核对；不伪造用户确认、验收、token 或执行成功。
3. 迁移幂等，重试不重复生成任务、成果和事件；迁移版本与前后数量有报告。
4. 备份覆盖数据库及必要附件，恢复后引用可达；敏感凭据按独立秘密管理规则恢复，不嵌入普通项目导出。
5. 恢复旧备份后重放删除/撤回清单，避免已删除资料复活。
6. 黑板、索引与摘要可从权威数据重新生成，重新生成不会制造业务任务或完成记录。
7. 迁移验证失败保留回滚点，不覆盖唯一旧数据；恢复运行器前先核对外部副作用与活跃执行权。
8. 不把“文件复制成功”当成业务恢复成功，必须完成查询、附件读取和状态一致性验证。

## 5. 发布门槛与证据格式

建议分三类验收，不得相互替代：

1. **代码不变量与故障测试**：A01–A10、A14–A16、A18–A20 的确定性部分通过；记录真实数据库状态及调用次数。
2. **模型质量与上下文测试**：A11–A13、A17 使用固定数据集、固定模型配置和盲评/规则评分；保留失败样本及真实输入。
3. **真实运行器与人工端到端测试**：至少一个已接入 AI 运行器及一个人工操作者走通 A04、A07、A08、A15；运行器不具备的能力明确标为未支持，不用模拟结果冒充。

每个测试结果至少保存：

```text
case_id
product_commit / schema_version / protocol_version
runtime_adapter / model / model_config
fixture_version / task_id / run_ids
started_at / completed_at
expected_assertions / observed_assertions
event_ids / artifact_version_ids / input_snapshot_ids
failure_injection_point（如适用）
token_and_cost_totals（含 unknown 项）
result: passed | failed | blocked | not_run
evidence_locations
```

测试完成记录不能包含秘密凭据。公开展示可使用脱敏证据；受限原始证据保留独立权限。
