# v0.6.1 实现与验收入口

本文件描述 v0.6.1 的实现与验收入口，包括后台智能分拣、项目记忆及合入的 Desktop DSH rc.2 适配。同目录其余文件是设计及协议参考，不能把参考 DDL 当作已部署的数据库结构。具体版本是否通过校验，以该安装包源 SHA 对应的完成记录和工作流证据为准。

## 应用入口与后台闭环

保留原有总览、任务、成果、Agent 执行界面；不新增“协作”导航或台帐/黑板/总结管理页。台帐和黑板由程序维护，项目总结由系统 AI 生成，三者供后续 Agent 按预算读取。

原“待办”输入默认先保存原文，再智能分拣。明确需求可以创建现有 Task；模糊输入和普通想法保留记录，重复任务只关联确定存在的任务 ID。用户可选择“手动待办”，或使用明确的 `[]` 前缀走原创建流程。手动创建阶段绕过 AI 分拣和改写，保留人工填写的任务内容；创建事实仍进入台帐，并可触发后台项目总结。后台总结失败不影响手动任务的保存。原有手动 Agent 派发继续由用户明确发起。

模型能力来自用户 Agent 配置列表的第一项，顺序不是默认 Agent、星标或工具目录顺序。首项不可用时明确记录失败，不静默换第二项。用户无需额外填写模型 API。分拣与总结是系统请求，不伪造成业务任务或业务执行会话；它们不会自动派发用户的任务。

台帐关键业务事件触发后台总结，连续事件合并，同项目一次只运行一个总结请求。总结固定来源版本，迟到结果保留为历史而不覆盖最新进展。总结提出的下一步行动进入独立建议，在原项目区域轻量提醒；只有逐条确认后才能创建任务。拒绝、过期和重复建议均留有记录。

- `src/data/collaboration.ts`：任务状态机、不可变要求/条件/成果/验收、依赖图、幂等回执、版本守卫、领取代次、预算预留、资料失效传播、机器上下文与导出。
- `src/data/intelligence.ts`：原始需求、分拣结果、项目总结版本和建议确认；共享现有任务模型。
- `src/data/repository.ts`：唯一业务数据源；协作命令与原有人工操作在此汇合。
- `src/data/runtimeDataSource.ts`：把外部执行事件关联到领域运行；会话结束不等于任务验收。
- `src/data/runtimeSubmission.ts`：实际 CLI 回传协议 `quandeck.runtime.v1`。设计目录里的 draft JSON Schema 不直接作为该通道的运行时协议。
- `src/components/journal/`：原待办输入、分拣状态和建议确认的最小界面调整。
- `desktop/app/local-store.mjs`：主进程 SQLite、旧数据迁移、不可变事实索引、备份和附件。

## 存储与事务

桌面数据位于 Electron userData 下的 `workspace/workspace.sqlite`。数据库包括：

| 表 | 职责 |
|---|---|
| `documents` | 项目库、运行适配器记录、偏好等有版本的文档；项目库 Snapshot 是业务当前状态的权威来源 |
| `immutable_facts` | 从项目快照中提取的不可变事实与 SHA-256；这是同一事务的完整性索引，不是另一个业务源 |

这是兼容现有 v0.5.1 Snapshot 的 SQLite 落地方式，没有同时维护设计 DDL 中的 30 张业务表。业务状态改变与新增事实在一个 `BEGIN IMMEDIATE` 事务内提交；任何旧事实被修改或移除，整个保存回滚。SQL 触发器还会拒绝对事实索引的直接 UPDATE/DELETE。SQLite 使用同步 FULL、回滚日志和单主进程写入；不依赖模型维护锁。

不可变索引覆盖：specs、decisions、artifacts、submissions、reviews、checkpoints、events、contextPackages、receipts，以及 intelligence 中的 intakes、classifications、summaryVersions、suggestionEvents。任务当前状态、运行状态、提案处理状态、资料有效性和当前策略是可更新投影。更新它们必须经过业务命令，不能通过修改历史来完成。

首次启动从旧 `workspace.json` 导入，保留原文件与 `.pre-sqlite` 备份。数据库建立后不再读取旧 JSON 作为当前数据。损坏数据库会阻止启动并保留原件，禁止默默重置为一个空项目库。现有历史完成只标记历史来源，不补造验收记录。

附件保存在 `workspace/attachments/<project>/<id>`；写入返回 SHA-256。备份包含数据库、一致性复制的附件以及逐文件 SHA-256 manifest。备份路径由用户通过原生对话框选择。恢复前退出应用，校验 manifest，把完整备份复制到一个新的隔离 userData 目录验证，再替换正式 workspace；不要用旧 JSON 覆盖已迁移数据库。

## AI 与程序的边界

程序签发 project/task/run/context 身份、要求版本、领取代次与权限。Agent 只能回显绑定，并提交候选成果、检查点、规划提案或阻塞原因。回传是严格的整条 `<quandeck-submission>` JSON 消息，普通自然语言不作为业务命令。未知字段、错误身份、过期领取、无效来源和重复键换载荷均拒绝。

- 人工任务没有伪造的 AI 会话、运行和 tokens。
- AI 成果进入待验收；接受验收必须逐条满足当前要求。
- 修改用户条件、要求或依赖会使旧执行失去提交资格。
- 新运行固定上下文版本；上下文保留用户条件，按预算挑选已验收资料，项目总结作为带来源版本的辅助判断，默认不复制旧会话全文。
- 资料过期或上游失效会传播到依赖成果，并要求重新核对。
- 规划建议先成为提案；采用后才创建可执行任务，不把模型建议冒充用户决策。
- 外部受理不明时保留未知状态和预算占用，先对账，不能盲目重复派发。

## 系统分析与手动 Agent 执行能力

“连接可以手动执行任务”和“连接可以用于后台只读分析”分别校验，连接握手不能代替系统分析的能力确认。

| 配置工具 | 用户手动派发 | 后台智能分拣与项目总结 |
|---|---|---|
| Codex | 使用现有任务执行适配器 | 有只读系统适配；每次新建临时目录及源会话，校验无网络的只读沙箱、空继承指令和禁用 MCP 等有效配置；不能确认时不启动模型请求 |
| Claude Code | 使用现有 SDK 执行适配器 | 有系统适配；通过已安装的官方 SDK 显式关闭执行工具、MCP、文件系统设置、skills、plugins 和历史会话恢复，并校验源端回执 |
| Desktop DSH／DSH `0.2.0-rc.2` | 支持新任务、公开输出、实际用量及同一存活 SDK 进程内续聊；Windows Desktop 启动器按已知模板解析 | 尚无已验证的只读系统分析适配，不能因手动派发可用而开放后台分析 |
| 其他工具 | 以实际已适配协议和连接能力回执为准 | 未提供系统适配的工具明确返回不支持 |

Windows Desktop DSH 只解析受支持的 `dsh.cmd` 模板，使用安装目录内的 Electron／ASAR 入口，不解释任意 batch 内容，也不要求用户另填 Node 来替换其运行环境。rc.2 的能力回执明确标记不支持跨进程恢复和 QuanDeck 权限决定回传：停止进程、崩溃或退出后不能用旧会话 ID 冒充恢复；不接管现有 Web GUI 会话；未获源端授权的操作不能由工作台自动批准。运行窗口按 `protocol` 和 `controls` 显示可用操作，适配器在实际操作时再次拒绝不支持的恢复。

后台分析始终选择用户配置列表的第一项，不根据默认 Agent、星标或安装目录顺序换用其他连接。若第一项是 DSH 或其他尚不支持系统分析的工具，分拣与总结保留原文、记录失败并提供重试；手动创建和该工具已支持的手动执行能力仍可使用。系统 AI 请求与业务 Run 分开记录，但共享项目预算；未知实际用量继续占用预留。

相关实现分别位于 `scripts/runtime/system-assistance.mjs`、`src/data/aiProvider.ts`、`src/data/intelligenceRuntime.ts`，以及手动执行侧的 `scripts/runtime/driver.mjs`、`scripts/runtime/dshDesktop.mjs` 和 `scripts/runtime/dshVersion.mjs`。

## 能力范围

这是本地桌面协作工作台，并非多用户云端租户系统。浏览器预览仍使用原有 localStorage，主进程数据库保护以桌面版为准。SQLite 防止应用正常接口改写历史，不声称防止拥有同一操作系统账户权限的程序替换数据库文件。

上下文预算使用保守估算，适配器提供的实际用量与未知用量分开记录。工作台能限制派发、并发、重试和继续运行；已经发出的外部模型请求可能产生迟到费用。不能把不能证明的第三方 CLI 能力标成硬沙箱或绝对费用上限。

归档保留历史。常规 UI 不提供物理抹除不可变事实的快捷入口；彻底删除用户数据应作为明确的维护操作，并同时处理附件及备份。本版本不提供云端同步、向量数据库或任意历史时点重建；这些不是台帐、上下文分包和人机交接的依赖。

## 校验

运行 `pnpm exec tsc --noEmit`、`pnpm test`、`pnpm build`。`desktop/local-store.test.mjs` 覆盖迁移、损坏保护、多句柄读取、不可变事实、事务回滚和备份恢复。领域与运行协议测试位于 `tests/collaboration.test.ts` 和对应 runtime 测试。

三个安装包工作流在原生 macOS arm64、macOS x64、Windows x64 中安装、启动和卸载。隔离启动先验证空工作区，再执行「人工任务 → 用户条件 → 有预算上下文 → 候选成果 → 逐项验收 → SQLite 防篡改」闭环；不会在真实用户目录里写入示例任务。v0.6.1 发布脚本要求这些检查成功，并核对源 SHA、安装包 SHA-256 和 GitHub 上传后的 digest。安装检查使用原有任务界面，不创建协作导航。

Windows 构建另运行 `desktop/check-windows-dsh-launcher.mjs`，检查真实 Windows Electron／ASAR 启动环境与 rc.2 协议测试端之间的新建执行、同进程续聊和关闭后拒绝恢复。该检查使用受控协议 fixture，不调用用户的 DSH 模型，也不等于完成企业 xLink 客户端端到端联调。

### 真实模型验收证据

自动测试中的协议 peer、mock SDK 和原生安装 smoke 分别验证协议守卫、数据闭环与安装运行，不证明用户账户下的真实模型已成功完成智能分拣或项目总结。`probeCodexSystemConnection` 只创建临时会话检查有效能力，不调用 `turn/start`；其成功不能记录为真实推理成功。即使某一手动 Codex 对话曾测试成功，也不能自动扩大为本版本所有后台 AI 功能的验收结果。

本次另实际发起过一次使用生产 schema 的 Codex 分拣请求：源会话已建立，但请求在 90 秒后超时，没有返回分拣结果或实际用量。CLI 内部日志记录 `sampling_error=request timed out`；应用层没有重试，CLI 内部进行了 4 次 stream 重试，后续总结请求未发出。没有观察到 schema 错误不等于已证明源端接受该 schema。此次真实源端连接与请求尝试应记录为“超时，成功链路未通过”，不能称为未调用真实模型，也不能称为真实智能分拣已验收。

真实模型验收须另行记录安装包及源 SHA、目标平台、首项连接工具和 CLI／SDK 版本、真实源会话 ID、实际用量或明确的未知值，以及各步骤结果：

1. 明确用户需求先持久化，真实模型返回分拣结果，原文约束与时间精度完整保留，创建任务但不自动派发。
2. 人工或 Agent 交付触发带固定来源的后台总结，模型不能改写确认条件或把候选成果标成完成。
3. 总结建议经用户逐条确认后创建任务；拒绝、重复、过期结果和失败重试维持各自守卫。
4. 首项连接不支持系统分析时明确失败、不偷偷切换工具，手动创建仍可保存。

尚未取得上述目标机器和真实账户证据的组合，应标为“真实模型链路待验收”。DSH 手动链和 Codex／Claude 系统分析链分别记录，不能由某一条链路的测试结果推定另一条已经验证。
