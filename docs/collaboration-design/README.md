# QuanDeck 人机协作后端设计

版本：设计 v1，2026-11-16。基线：QuanDeck 0.5.0，commit e8cb0ab68eb1c30b3efd121dd33680f49e1ace5c。本文定义目标架构及实施约定，不代表这些能力已进入应用。

v0.6.0 的实际代码入口、存储结构和验收方式见[实现说明](implementation.md)。本设计参考 DDL 与运行协议的区别以实现说明为准。

目标是让所有纳入管理的 AI 与人工任务有身份、有责任人、有依赖、有成果、有验收，并让新会话仅加载完成当前任务所需的材料。验收范围包括工作台创建、工具接入、导入和人工登记的任务；未接入的外部工作不承诺自动发现。

## 1 核心设计决定

1. Task 是稳定的工作身份；Run 是一次执行；Session 是与模型/工具沟通的上下文容器。一个 Task 可有多个 Run 和 Session，人工 Task 可以没有 Run 或 Session。
2. 任务要求、用户决定、成果和上下文包具有不可覆盖的版本；当前名称、状态、责任人、采用指针可通过受控命令变更。
3. 代码拥有状态转移、权限、预算、写盘与派发权；AI 提供候选计划、研究、成果、解释、下一步建议。AI 说“完成”不构成完成事实。
4. 台帐是结构化任务数据的权威查询入口；黑板是当前协作状态的派生视图。Markdown 文件是可读导出，不是第二套数据库。
5. 只对边界独立、有交付物或需要不同执行者的工作拆任务。重试、更换模型和压缩续做保留 Task ID。
6. 正常执行不能覆盖已提交历史；纠错追加版本。受控隐私删除是明确例外，不以“审计不可变”阻止数据删除。
7. 新结果先提交、再验收、再供下游默认采用。已验收也不等于永久有效，时效与验收分别记录。
8. 选择本地 TypeScript 模块化单体、SQLite 与附件文件。多人跨设备协作后续使用服务端数据库，不能将 SQLite 文件放网盘当作同步方案。

阅读顺序：[数据模型](data-model.md) → [代码与 AI 协议](agent-protocol.md) → [工作流](workflows.md) → [验收矩阵](acceptance.md)。SQL 和 JSON Schema 是可检查的设计工件，不是自动应用到生产的迁移。

可直接查看[项目说明示例](examples/PROJECT.generated.md)、[台帐示例](examples/ledger.generated.md)、[黑板示例](examples/blackboard.generated.md)。示例导出的export_content_sha256按去掉首行hash声明及其后空行后的UTF-8正文计算，避免文件自包含hash循环；生产可使用独立manifest保存文件hash。协议示例中的短ID用于易读夹具，不替代生产ID分配规范。

设计包检查命令：python3 docs/collaboration-design/check_design.py（Python环境需有jsonschema）；它校验SQL约束、协议样例、内容hash、预算算术和文档引用，不运行目标后端。

## 2 后端模块以及代码与 AI 的职责

现有 Electron 主进程已经拥有业务 Core，renderer 通过命令和 Snapshot 访问业务。保留这个边界，将写盘和核心守卫从全量快照变更收敛到命令处理器。

| 模块 | 代码必须完成 | AI 可以提供 |
| --- | --- | --- |
| Command Gateway | 鉴权、会话绑定、参数校验、限额、幂等、错误码 | 通过工具发起允许的命令 |
| Project / Task Service | ID、版本、责任人、状态、依赖、范围、创建与修改事务 | 候选任务标题、拆分、估算、关联建议 |
| Policy Service | 判断已有授权、预算、工具能力、停止条件；记录授权快照 | 解释为什么需要某工具或新增权限 |
| Planner | 保存计划草稿、检验依赖DAG、去重、对比范围、采用计划 | 理解需求、检索历史、规划任务与专业方法 |
| Context Builder | 权限过滤、固定版本、token预算、快照与哈希、提供引用读取工具 | 候选材料排序、摘要、缺口分析 |
| Scheduler | 从就绪任务领取、并发限制、预算预留、人工容量、outbox派发 | 给出优先级和工作量建议 |
| Runtime Adapter | 接通Codex/Claude/其他工具；源会话、真实回执、控制与能力检测 | 执行任务、提问、写检查点、提交结果 |
| Artifact Service | 保存内容与来源、生成版本、引用校验、访问控制、有效期 | 研究结果、代码、文档、判断、摘要 |
| Review Service | 运行确定性检查、执行验收政策、记录review并推进状态 | 按rubric给出语义质量评估与证据 |
| Ledger / Blackboard Query | 从同一事实读模型查询、过滤、分页、导出、订阅变更 | 补充解释性摘要，不能生成责任人或完成状态 |
| Event / Recovery Service | 原始回执、事件去重、丢包核对、租约接管、重放outbox | 可建议恢复动作；不能伪造成功 |
| Usage / Audit | 从adapter收用量、预留与结算、人工计时、记录变更来源 | 成本估计；不能填写实际计费token |

AI 是可更换的能力提供者。主调度与事实管理在代码中运行，因此即使 AI 暂时不可用，人工仍能创建、领取、提交和验收任务，台帐及黑板仍可读取。

AI规划也有身份：代码为需求建立范围仅为规划的Task和purpose=discussion的Run，按同一协议返回plan_proposal并计费。AI复核使用独立review Task和purpose=review的Run，其输出仅为advisory，不能抢占产出任务的主执行权。人工验收无需AI Run；验收合法的历史提交不要求产出Run继续维持活租约。

建议在现有仓库增加以下边界，而非一次重写所有 UI：

    src/domain/                 命令、实体规则、状态机、政策
    src/application/            用例：创建、计划采用、派发、提交、验收
    src/infrastructure/storage/ SQLite仓储、事务、文件与备份
    src/infrastructure/runtime/ 工具适配、能力与真实事件映射
    src/context/                检索、上下文装配、摘要与引用解析
    src/queries/                Snapshot兼容、台帐、黑板、成果查询

这些是建议路径，尚未创建生产模块。服务间首先是进程内调用；桌面 IPC 和未来 HTTP/MCP 共用同一命令处理器，不能分别实现两套完成规则。

## 3 数据对象与身份规则

详细字段与 SQL 见 data-model.md 和 schema.sql。以下给出用户与产品应共同理解的含义。

| 对象 | 业务含义 | 关键规则 |
| --- | --- | --- |
| Project | 一个有边界的目标集合 | 有目标、政策、时区、预算与成员/本地用户 |
| Task | 可独立验收的工作 | ID不随换会话改变；owner负责交付，executor负责本次执行 |
| Task specification revision | 某时刻的目标、交付物、验收条件 | 发布新要求生成新版本；历史运行仍绑定原版本 |
| Dependency | 执行或成果依赖 | 区分blocks与references；只有blocks阻止启动；禁止自依赖和环 |
| Run | 一次有边界的执行尝试 | 关联输入包、执行者、租约代际、预算、结束原因 |
| Session | 外部工具或模型会话 | 保存provider与真实源会话ID；新上下文与原会话resume明确区分 |
| Artifact / version | 可复用交付物及其版本 | 保存来源、范围、核验时间、适用条件、接受状态 |
| Constraint / Decision | 用户条件与正式决定 | user_confirmed与AI hypothesis严格分开 |
| Review | 针对具体成果、要求版本的验收 | 包含检查项、结果、证据、审查者及policy版本 |
| Event / receipt | 什么命令在何时造成什么变化 | 服务分配时间/序号；身份由可信入口给定 |
| Context package | 本次模型确实收到的输入版本 | 固定引用、规则版本、删节说明、token估算/实测 |
| External action | 有外部副作用的动作 | 有授权、幂等键、回执与unknown状态 |
| Projection | 可重建的台帐/黑板/搜索缓存 | 不拥有独立事实，带生成序号与新鲜度 |

ID 用服务端生成的 UUID 等全局稳定标识。A5、C10、T83 是项目内显示编号，与数据库 ID 分离，重命名或移动不改变实体身份。不得用标题匹配替代身份。

区分三个版本数：
- tasks.version：任务业务状态的CAS版本；状态、owner、依赖和要求采用发生变化时递增。
- tasks.spec_revision：目标/交付物/验收条件的版本；心跳、展示排序和普通评论不改变它。
- tasks.claim_epoch：执行权代际；接管、撤销执行权时递增，用于拒绝旧运行写入。

心跳更新租约，不更新任务业务版本。提交时检查当前运行与要求是否仍适用；不能只因为某个无关UI字段变化就丢弃成果，也不能不经校验把旧要求的结果当作新要求已完成。

## 4 状态机和完成含义

Task 状态统一为 draft、ready、running、blocked、paused、in_review、done、failed、cancelled。

| 转移 | 触发者 | 代码守卫 |
| --- | --- | --- |
| draft → ready | 计划采用/任务发布命令 | 要求与验收可执行、负责人明确、前置满足、授权足够；否则blocked |
| ready → running | 人工开始/调度领取 | 版本一致、无冲突主运行、预算已预留、能力允许 |
| running → blocked | 缺输入/权限/外部条件 | 记录原因、需谁解决及相关Run；不得把等待时间算运行消耗 |
| running → paused | 明确暂停/恢复政策 | 停止或暂停回执另记；不把发出stop当作进程已经停止 |
| running → in_review | 有效成果提交 | 输入版本仍适用、引用完整、产物已持久化、执行权有效 |
| in_review → done | 验收通过命令 | 必需检查通过、必需子任务完成或有授权豁免、证据未失效 |
| in_review → ready/blocked | 退回修改 | 保存不通过原因；新Run继续同Task，旧成果不覆盖 |
| 任意非终态 → failed/cancelled | 服务/授权用户 | 记录原因，释放或核对资源；取消不等于外部副作用已撤销 |
| done → draft/ready | 显式重开 | 新要求/修订记录，保留原验收历史；重新检查依赖与权限 |

blocked是缺少推进条件，paused是明确暂停；二者不互相替代。解除阻塞后按当前条件回到ready或有效的running，不能盲目恢复。

Run 独立使用 queued、running、waiting_input、waiting_permission、paused、succeeded、failed、cancelled、lost。Run succeeded 只表示该次执行正常结束，若没有有效提交，Task仍不能done。反过来，人工任务完成不要求存在Run。

父任务完成不是所有子任务状态的简单平均。必需子任务完成和集成成果通过验收后才能完成；取消必需子任务需修改范围或记录豁免，不能将取消当完成。

历史任务done之后证据过期，不改写当时验收历史。将相关成果标记stale、当前方案标记needs_revalidation，创建复核任务或显式重开。默认检索不得无提示地使用已过期成果。

## 5 台帐和黑板怎样创建

创建项目是一条确定性业务命令：
1. 验证项目输入与操作者。
2. 单事务创建Project、默认Policy、事件序列起点；初始化默认查询配置。
3. 返回项目ID、版本与ProjectCreated事件。
4. 台帐查询立即可返回空列表；黑板立即返回“未设置任务/无当前阻塞”，不调用AI编造摘要。
5. 文件导出器按需生成PROJECT.md、LEDGER.md、BLACKBOARD.md。导出失败只显示导出状态，不回滚已持久化任务，也不能报项目创建失败让用户重复创建。

台帐展示全生命周期的可查询任务记录，可按状态、owner、时间、标签、实体及成果类型分页。它不保存所有会话全文，使用引用链接连接成果和原始记录。

黑板默认包含：
- 当前目标和当前要求版本。
- 正在执行：Task、executor、Run、最新检查点时间。
- 等我处理：待确认条件、待验收成果、权限或预算决策。
- 受阻：阻塞原因、依赖及解决人。
- 接下来可做：已满足依赖且符合授权的任务，带owner与计划时间。
- 最近完成：已通过验收的成果链接。
- 可选AI摘要：明确标记为解释，显示source_seq与生成时间。

当前权威状态建议直接查询同库记录，保证写后读一致；只有摘要、搜索和导出文件异步生成。页面可显示最新事实与略旧摘要，但不得用旧摘要覆盖最新状态。摘要落后时标为“摘要待更新”。

每个导出文件标明 project_id、generated_at、source_seq、schema_version、内容hash、回源查询方式。它是某一时刻的快照。导出的黑板不是自动执行计划，也不携带授权凭据。

## 6 读写规则和不可覆盖边界

**所有业务写入必须经过命令服务。** AI、renderer、外部适配器都不能直接UPDATE数据库或覆盖台帐文件。

角色范围由项目成员关系和任务分配共同决定：owner可修改项目政策/预算、分配责任与发起擦除；contributor只可编辑授权任务和提交成果；executor只可读获准材料并提交本Run内容；reviewer只可验收被分配的提交；reader只读。服务身份只执行其专用命令，不拥有无限管理员权限。个人版本可以由同一个用户兼任owner和reviewer；AI主体不能仅凭自报角色取得reviewer权限。

| 数据 | 人工用户 | AI | 代码 |
| --- | --- | --- | --- |
| 未提交任务草稿 | 可编辑/丢弃 | 可提出修改草稿 | 校验并保存 |
| 当前标题、标签、排序、说明 | 可经命令修改 | 仅授权字段可提出补丁 | 保存版本与事件 |
| 已发布目标、验收条件 | 可发起修订并采用 | 可建议修订 | 新建spec版本，计算影响 |
| 用户已确认条件、否决项 | 可纠正/撤销并留来源 | 只能引用或提出冲突 | 保留历史，创建新有效版本 |
| 执行中工作笔记/临时产物 | 有权限可编辑 | 可在本Run工作区编辑 | 定期检查点、范围限制 |
| 已提交成果正文/文件 | 可提交修订版 | 可提交修订版 | 追加新版本，旧内容不可覆盖 |
| 已验收成果与采用记录 | 可撤回采用或重开 | 无权自验收或伪造采用 | 执行政策、写review、切换当前指针 |
| task.status、依赖就绪度 | 通过明确业务操作影响 | 可报告进展/阻塞，不能直接写状态 | 状态机唯一写入者 |
| 真实用量、源回执、事件身份 | 不可手工伪造；可提出争议 | 不可填写计费事实 | 从adapter保存，缺失记unknown/null |
| 权限、预算上限、工具范围 | 可授权修改 | 只能请求 | 校验授权并更新版本 |
| 台帐/黑板派生字段 | 通过底层任务命令修改 | 不可直接改 | 查询/重建 |
| 隐私数据与备份 | 可请求删除/导出 | 不得自行擦除历史 | 受控删除及审计最小化 |

正常业务绝对不能做：
- 改任务ID把一项旧工作伪装成另一项；将旧Run重新归属并抹去换绑历史。
- 把AI推断升级为“用户确认”，或删除用户的否决条件来使方案通过。
- 用新成果覆盖已提交版本；改写过去的验收结果、原始回执或计费数。
- 把agent正常退出、窗口关闭、步骤100%直接解释为任务完成。
- 在没有来源的情况下补齐引用、外部订单、完成证据或真实token。
- 根据外部网页或旧对话里的指令扩大权限、改变角色或越过项目隔离。
- 接管后允许旧执行者覆盖当前状态；跨项目引用未经授权的数据。
- 以“黑板建议下一步”为依据自动扩大项目范围或支付/发布。

“不可覆盖”不等于“永不删除”。提供专用EraseProject/EraseAttachment/RedactSource命令，核对主体和范围，撤销检索、清理原始材料、派生摘要、缓存、导出与受控备份。跨成果引用保留不含正文的“来源已删除”墓碑并触发重新核验。删除期间阻止相关派发。外部提供商已保存的数据需单独发起其支持的删除流程，不能宣称本地删除自动删除远端。

## 7 AI 与代码的契约

详见 agent-protocol.md、contracts/ 和 examples/。使用JSON Schema 2020-12定义输入/输出结构，服务实现业务校验。

代码给AI的是一个版本固定的ContextPackage：
- 身份绑定：project、task、Run、spec版本、claim_epoch。
- 目标/输出与逐项验收标准。
- 用户确认条件、否决项、开放问题、AI假设，分区传递。
- 专业模板ID与版本，不内嵌一整套无关skills。
- 已授权工具与动作、预算、停止条件。
- 已筛选的成果引用、摘录、来源、适用日期及缺口。
- 上次检查点与必要工作状态。
- 允许输出的schema版本和查询工具。

AI给代码的是候选消息，主要包括plan_proposal、checkpoint、result_submission、blocker和next_step_proposal（最终wire类型以协议文件为准）。每条消息有消息ID和幂等标识；真实身份、时间、Run与权限由网关从调用通道绑定。

结果的接收顺序：
1. 解码并限制大小、深度、数组长度；拒绝未知schema或未知字段。
2. 从凭据绑定actor、project与Run，不信任AI文本自称的身份。
3. 检查幂等键和payload hash。同key同内容返回原回执；同key不同内容冲突。
4. 检查任务业务版本、spec版本、claim_epoch、运行状态、当前授权。
5. 检查引用存在、可访问、内容hash/版本一致、成果时效。
6. 语义与确定性验收分离；检索来源存在不代表结论已被证明。
7. 在事务中保存提交、事件、状态和outbox，返回明确回执。
8. 成果验收通过后，代码触发投影更新和下游就绪检查。

AI自然语言回复保持普通文本。结构化提交走单独tool/message通道，不能扫描一段普通聊天出现“完成”“confirmed”就改状态。旧工具只提供文本时，解析器只能产出待校验草稿；不支持的能力显示手动回收。

## 8 上下文检索与预算

先过滤，再排序，最后装配。数据库查询和权限判断先于向量/语义检索，避免把不该访问的数据交给模型后再要求忘掉。

分层输入：
- L0：任务契约、必需用户约束、权限与停止条件，始终包含。
- L1：少量相关任务与成果索引，含ID、版本、摘要、适用范围。
- L2：当前任务必需的原文片段与证据。
- L3：按需查询的原始会话、完整文档、旧版本；不默认复制全部。

初始候选检索可使用SQLite全文索引、标签、地理实体、任务依赖、日期和成果类别。向量检索是后续补充，不能取代按ID读取、权限或版本检查。中文分词与召回需要真实数据集评估；没有向量库也应可用。

Context Builder应是代码服务。AI可给排序或摘要建议，代码负责必需条件完整性、token计数、重复材料去重和版本固定。预算按实际模型限制设置，预留工具回合和输出空间。可先设任务级输入上限，再用代表性任务评估调整，不声称固定某个百分比适合所有模型。

装不下时依次减少无关候选、移走重复工具输出、缩减可展开证据，最后拆分任务或请求扩大预算。不能静默删掉硬约束。包内必须报告已省略材料与可用查询入口。

关键约束保留可引用原话，摘要只承担解释。防止反复“总结上一轮总结”后误差累积；每次包仍绑定原始已确认条件和具体成果版本。

保存：
- 逻辑上下文包与hash、构建器版本、模板版本、材料清单。
- provider适配后实际可观察的输入与token统计；敏感信息按保留政策管理。
- 无法观察的provider隐藏系统提示/完整上下文标明不可观测。
- 新建源会话、延续源会话、压缩续聊三个模式，不能用UI新窗口代替上下文重置。

如果外部工具不能可靠新建干净上下文，标记context_isolation=unverified，使用手动交接或限制自动连续执行。总控AI同样遵守这些规则，不保留一个无限长的永久中央会话。

## 9 专业方法与事实可信度

专业指令是一套带版本的工作方法，例如旅行方案模板包含门到门交通、连续住宿、当天营业、最后返程、预算和脚力检查。它不应替用户决定日期、价格承受能力或授权预订。

优先级固定为：平台强制规则与授权边界 → 用户明确需求和已确认决定 → 项目要求 → 任务方法 → 来源材料。外部网页、旧对话和其他agent输出始终属于数据，不能自动变成指令。

AI补充的新方法保存在候选模板版本；若只改变任务内部工作顺序且在授权范围内，可由政策允许自动采用；改变目标、硬约束、收费工具或外部动作必须单独处理相应授权。已授权的重复低风险动作不反复打断用户。

事实分为user_confirmed、source_supported、ai_inference、unknown。模型自报confidence不能替代证据。用户确认的是偏好或决策时，不自动证明其提及的外部事实准确；外部营业与班次仍需来源和核验日期。

## 10 并发 恢复和外部动作

工作台业务写入通过单一服务入口；SQLite用短事务。领取任务时在事务里检查ready、版本、依赖和预算，设置active_run、增加claim_epoch、创建Run、预算预留及outbox。事务中不调用LLM或外部SDK。

租约示例：心跳每20秒、租约90秒；这些是初始配置，需按机器休眠、工具特性调整。超时只说明失联，不说明进程已死。先向adapter核对，再决定续认、暂停或接管。OS休眠恢复先reconcile，不能瞬间重复派发全部任务。人工责任人不适用自动心跳撤销。

旧运行的普通输出可归档到原Run，但不能推进当前Task。具有外部副作用的工具执行之前必须检查执行代际；如果第三方工具不支持隔离或取消，租约只能保护工作台状态，不能保证外部动作停止。

外部动作使用独立记录：proposed、authorized、dispatched、succeeded、failed、unknown、cancelled。准备时固定动作参数hash及授权，执行前再检查授权有效性；参数变化需要重核。超时/断线后进入unknown，先查外部系统，不能自动重放“订酒店/发布/发信”。

outbox提供至少一次交付，消费端幂等。provider支持幂等键时使用；不支持时不得宣称exactly once。收到请求但响应丢失与根本未收到请求不同，恢复流程必须保留这个不确定性。

数据库提交成功后应用崩溃：outbox恢复派发。派发成功但回执丢失：依dispatch/外部幂等键查询与核对。投影失败：重新构建，不能重复执行任务来“修复黑板”。

预算包含总控、子agent、检索、摘要、重试、输入/输出和缓存计费；人工计时单独记录。启动前预留，结算时以adapter用量替换估计并释放余量。用量未知时保留预留并标记unknown，不能以0继续无限运行。关闭任务自动释放预算前先核对仍在运行的外部执行。

费用默认按项目计费币种比较；多币种保留原币数额并分开显示，若需要合计则另存换算汇率、来源与时间，不能直接相加。累计token与增量token、父调用包含子调用的口径也必须由adapter声明，统计时去重。

## 11 存储与文件布局

建议一个本地profile一份SQLite，项目共享同一数据库事务边界；所有表按project_id隔离。文件位于Electron userData/collaboration下，不能放进被agent自由编辑的项目源码目录。以下路径与data-model.md一致；PROJECT.md是额外的可读项目说明导出。

    userData/collaboration/
      collaboration.sqlite
      blobs/<project-id>/<blob-id>
      projections/<project-id>/generation-<seq>/PROJECT.md
      projections/<project-id>/generation-<seq>/ledger.json
      projections/<project-id>/generation-<seq>/ledger.md
      projections/<project-id>/generation-<seq>/blackboard.json
      projections/<project-id>/generation-<seq>/blackboard.md
      projections/<project-id>/current.json
      backups/<backup-id>/manifest.json
      backups/<backup-id>/...
      run-workspaces/<run-id>/...

连接凭据保存在系统凭据存储，模型上下文、导出、普通日志中只保留引用。使用受支持且已修复已知问题的SQLite版本；启用foreign_keys、适合本机并发的WAL、busy_timeout，定期checkpoint。不要通过共享网络文件系统直接访问WAL数据库。[SQLite适用场景](https://www.sqlite.org/whentouse.html)；[WAL约束](https://www.sqlite.org/wal.html)。

大附件不塞进每个任务JSON。流式写临时文件、校验大小与hash、原子rename到不可变blob路径，再提交数据库引用。数据库保存内容hash，可在同profile/授权范围内去重。数据库事务失败形成孤立文件，可延后GC；引用未完成上传的文件不能作为有效成果。删除前检查所有合法引用。

备份使用SQLite在线备份接口或等效一致性机制，并生成附件清单及hash；不能只复制活跃db而漏掉WAL。恢复时检查schema、DB完整性、FK、附件缺失与引用hash，然后停留在paused/reconcile状态，不能自动重放外部操作。保留最近备份与保留期由用户配置；删除请求同时处理可控备份或按明确期限清除。

删除登记独立于可能恢复的旧备份保存，恢复前合并登记以避免已删除内容复活。无法回收用户自行分发的离线导出或第三方副本，应准确记录范围。

同一OS账号下给agent无限shell权限时，单靠API设计不能保证它无法直接改文件。受控执行需要进程/文件系统沙箱或独立权限，仅给run工作区写权限，通过短期受限token访问网关。无法落实隔离的adapter标明权限边界未验证，不给自动高后果动作权限。

## 12 逻辑链条和自动推进

统一链条：

    需求登记 → 解析与检索 → 候选计划 → 采用/政策校验
    → 固定任务要求与依赖 → 就绪队列 → 上下文包
    → 领取并派发 → 执行与检查点 → 提交成果
    → 验收 → 写入正式成果与事件 → 刷新台帐/黑板
    → 解锁下一步或结束

其中AI负责解析、规划、研究、提交内容；代码负责每次“从候选变成事实”的转换。候选下一步只能变成草稿；在已授权范围、依赖和预算都满足后代码才能让它ready并派发。

去重不能只看标题。采用计划使用proposal_id和幂等键；相似任务检索给建议，真正合并需要明确关联。一个任务被两条计划引用时保留同一task_id和独立依赖，不复制两份工作。

自动推进有全局停止条件：项目目标已验收、没有就绪任务、预算不足、关键条件缺失、权限不支持、达到最大重试/规划深度/无进展回合。遇到条件不足更新黑板“等谁解决”，不持续调用模型空转。对已授权且可执行的任务无需每次重新询问用户。

完整主流程、人工流程、回收与错误恢复见 workflows.md。

## 13 从现有实现迁移

| 现有位置 | 可保留基础 | 目标变化 |
| --- | --- | --- |
| desktop/app/main.mjs ensureCore | Electron拥有Core、IPC与Snapshot | 挂载命令服务和仓储，renderer继续只读Snapshot/发命令 |
| desktop/app/local-store.mjs | 原子写workspace.json、附件目录 | 作为只读迁移源；新事务数据转SQLite，附件保留映射与hash |
| src/data/repository.ts WorkdeckDataSource | 现有业务接口、人工任务入口 | 保留UI适配外观，completeTask等转为受控验收命令 |
| src/data/runtimeContracts.ts | Run、Session、sequence、request、usage | 增加context_package、spec版本、执行代际、提交与review引用 |
| src/data/runtimeDataSource.ts brief | 已采用方法与当前任务背景 | Context Builder按需检索替代全量拼接 |
| readAgentConclusion | 可选结构化结论读取 | 独立schema通道；confirmed字段不能当用户确认事实 |
| settleRuntimeTask | 不因普通一轮结束立即完成 | 全部归档后最多进入可验收；必须review通过才done |
| runtimeDataSource事件处理 | 序号、重复事件、旧attempt保护 | 转为持久化唯一键、入站收据、事务与恢复游标 |
| src/data/search.ts及成果页 | 查询与展示 | 统一台帐/成果/黑板查询，增加source_seq与版本/时效 |
| scripts/runtime/* | 官方工具协议适配基础 | 能力矩阵、上下文隔离证明、幂等派发与副作用核对 |

迁移步骤：
1. 冻结写入窗口，备份旧JSON与附件，记录原schema与hash。
2. 导入到新临时数据库，保留旧ID到新ID映射，建立基础版本和来源。
3. 旧done保留legacy_imported完成来源；没有验收证据不能伪造review。默认作为历史成果，不自动满足要求严格验收的新依赖。
4. 核对项目/任务/会话/成果数量、关系与附件hash，报告无法映射的记录，原始资料保留。
5. 开启只读影子查询对照旧Snapshot，不派发任务，不双写两套权威库。
6. 对照通过后，单次切换写入口到新库，旧库只读。首次启动运行记录统一恢复到待核对状态。
7. 切换后若尚无新写入，可恢复旧备份；若已有新数据，必须导出/迁移新增事件，不能直接回滚旧库丢失用户工作。

## 14 分阶段交付与验收

P0：实体身份、命令入口、要求版本、用户条件、成果版本、人工提交与验收、事件记录、台帐/黑板确定性视图。完成后可以不用AI走通人工闭环。

P1：Context Builder、检索与专业模板、严格协议、真实Runtime适配、预算、租约、outbox与恢复。完成后走通AI→人工→AI的真实链条。

P2：在既有政策范围内自动规划/推进、批量影响分析、跨项目授权复用、质量/成本评估。多用户服务端协作单独验收成员权限、并发与同步，不以本地多窗口验收代替。

详细案例见 acceptance.md。实施时除已有工程测试外，必须覆盖断电点、重复回执、租约接管、条件变更、成果过期、用户删除、上下文膨胀和真实工具能力不足等场景。

## 15 设计边界

本包的SQL和协议示例可以做静态与约束自检，但不能由此宣称后端已实现、多人并发已通过或LLM质量已验证。产品验收需实际命令处理器、provider账号与故障注入。

不需要引入永久运行的“总控大脑”来维持事实，也不需要把台帐变成不断增长的巨型prompt。只要任务和成果外置、写入有守卫、检索与验收可测，模型与会话就可以更换而不丢失工作身份。
