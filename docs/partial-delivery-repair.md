# 部分交付与自动依赖修复

真实使用中，页面定位 Agent 明确提交了 `deliverySlotIds: []`，并列出“缺少源码定位”和“尚未完成交互验证”两项缺口。旧版把唯一交付槽的空数组当作字段缺省，显示了候选章节；依赖调度只检查已有候选，提前启动设计任务。与此同时，源会话仍允许输入，但台帐把任务标为待验收，提交补充信息时又被拒绝。

修复以黑板上的成果版本和台帐的提交记录为唯一依据：

- 显式空数组表示没有完成任何章节；仅旧数据未提供字段、任务只有一个槽、无未解决项时保留兼容映射。
- 交付槽未齐或存在实际阻塞缺口时，候选正文照常保存，但任务保持待补充，依赖不推进。可选改进记入 `nextSteps`；“候选尚待人工核对”不算阻塞。
- 任务所需槽全部声明交付且无阻塞项后，进入待核对，自动执行仅可在已批准的确切方向和计划版本内引用候选；这不等于人工验收。
- 对旧版已经误记为待验收的部分候选，地图和依赖派生立即纠正，不重写历史成果或提交。用户提交补充内容时，台帐追加 `partial_submission_continued` 事件，验证当前提交、任务版本、运行、领取代次、要求版本、租约和方向后，才允许原范围续作。用户回复超过等待租约时，只有仍持有同一执行权的 `waiting_input` 或 `paused` 运行可以在该明确操作中续租；过期执行中、已失联或终结的运行仍拒绝。
- 运行已终结、执行权已变化、方向过期、完整候选待核对时，仍不能通过普通续聊绕过。真实权限请求继续通过源权限协议处理，文本“同意”不会代替授权。
- 已经错误提前启动的历史下游运行保留，但其前置不足时不能继续执行或传播新成果。

验证：新回归 `tests/partial-delivery.test.ts` 覆盖上述真实结构、旧版状态、补充后重新交付、权限及版本边界。对本地真实项目的一致快照只读回放，结果为 5 个交付槽中 0 个填入、0 项完成、页面定位的 2 项缺口保留，后续设计依赖不可推进，快照内容未修改。类型检查、构建和领域测试通过；原生测试中仅三个本地端口测试初次受沙箱限制，单独允许回环端口后全部通过。原生 App 的最终交互验收由集成流程另行记录，本文不声称已安装或发布。

安装检查 `desktop/app/smoke-goal-delivery.mjs` 在隔离工作区通过生产命令创建两个人工任务、三个声明槽，逐阶段核对持久状态与原生页面：

| 提交 | 台帐任务状态 | 交付地图 |
| --- | --- | --- |
| 路线显式交付 `[]`，来源尚未核对 | 待补齐 | 路线、来源均缺失，酒店为空 |
| 路线交付一个槽，第二个必需槽缺失 | 待补齐 | 路线候选、来源缺失、酒店为空 |
| 路线及来源两槽交齐，无实际阻塞 | 待核对 | 路线及来源候选，酒店仍为空 |

检查还要求候选详情可打开、方向大纲与槽持久化、没有虚构 Agent 运行、没有自动写入人工认可。旧安装样例把“候选未人工认可”写入 `unresolved`，却期待候选状态，与修复后的阻塞语义冲突；现改为以上过程，不放宽缺项判定。Apple Silicon 的隔离原生启动检查已通过这三个阶段；这项检查只验证人工交付路径，真实 Agent 闭环及安装包发布仍需独立验证。
