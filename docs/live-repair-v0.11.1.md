# QuanDeck 0.11 实际项目故障审计与验收方案

审计日期：2026-11-17。基线：v0.11.0，源码提交 `f2fba51341addc507e74e56d60424f3b8a226015`。本文记录真实使用故障、源码边界和修复验收要求；修复安装包的完整实机验收必须另附执行记录，不能用单元测试或构建成功代替。

## 1. 事实与交付范围

本次检查使用实际项目的一致性 SQLite 备份，只读分析任务、方案、会话、执行记录及用户上传的截图。原始数据、完整用户文本、附件、源会话标识和权限请求仅留在本机，未纳入仓库。App 内提出的请求均按真实需求处理。

实际项目包含 5 个业务任务、4 个内部规划任务、5 个会话、29 次智能作业；24 次作业失败，5 次成功。失败中包括 4 次 120 秒超时和 20 次项目并发限制拒绝。备份时没有成果、提交或输出件；因此不能把“已有方向/任务树”描述为“已经完成用户任务”。

| 用户实际需求 | 应交付的内容 | 基线实际表现 |
| --- | --- | --- |
| 检查多 Agent 工作流、真源、重复入口与 mock，并提供项目体检和路线图 | 工作流用例、根因报告、架构边界、清退矩阵、优先级路线图 | 已讨论并分解；执行阻塞，无成果入库 |
| 从原始需求自动提炼任务标题 | 简洁标题，完整需求仍可查 | 长段需求和链接直接变成页面标题 |
| 修复方向页拥挤并实现合理布局 | 方向正文、大纲、任务图在大小窗口均可读 | 大窗口内容被挤在一小块区域，标题逐字换行，右侧大量空白 |
| 新任务输入支持粘贴截图 | 文本、截图和附件一次保存，不丢原文 | 新任务输入没有粘贴文件处理；其他输入区支持不能证明这里支持 |
| 解除讨论并发限制 | 讨论、归纳和独立执行分支互不被权限等待堵塞 | 多个权限等待耗尽项目并发名额，后续讨论及分解被拒绝 |

## 2. 故障链与源码依据

1. **待授权被隐藏。** `collaboration.ts` 将运行等待映射为任务层 `paused`，这是任务层较粗的状态。原 `projectActivity.ts` 先将执行的源会话加入“已代表”集合，再因任务 `paused` 跳过该项；后续会话循环又因“已代表”跳过，真实授权请求因此从当前执行区消失。用户看见暂停，却看不到使任务继续的按钮。
2. **一个等待堵住其他工作。** 原 `projectActiveCalls` 将非终态调用计入共同上限，等待权限也占名额；归纳、讨论、任务分解与执行共享门槛，造成真实数据中连续的并发拒绝。修复应按实际独立工作推进，不得以降低展示数量假装解决。
3. **执行意图只得到文字回复。** 用户已表达“支持，请执行”，会话仍回复“请点击执行”，没有持久化授权和启动状态转移。UI 文案认可不等于领域命令已被执行。必须用当前方向版本和正式转换命令记录一次授权，并让重复提交幂等。
4. **方向后续回包遗漏字段导致已有成果地图丢失。** 原 `projectWorkflow.ts` 按最新带任务的讨论结论物化计划；后续回包只带任务、不带交付清单时，先前明确的多个输出位被降级为任务级默认占位。合并需要区分“未提供”与“明确清空”，保留已有方向与输出位的版本关系。
5. **输入入口实现不一致。** `TaskInput.tsx` 已支持截图粘贴；`Composer.tsx` 新建输入入口未接入。手工输入默认路径又把全文直接存为标题。必须用真正的新任务入口回归，而非检查任意存在 `onPaste` 的组件。
6. **布局缺陷被长标题放大。** 用户截图显示主体列宽失衡。需结合 `direction-document.css`、`fullscreen.css`、`Workspace.tsx` 的父布局约束修复；仅截断标题不能修复页面列宽。
7. **最终回复没有变成成果。** 实际 Codex 适配器以 `waiting_reply` 表示一轮成功完成，而旧成果兜底只在 `done` 时运行；另有任意 checkpoint 或拒绝回执都会阻止后续成果收集。修复必须采用真实适配器成功信号，区分问题、阻塞、候选与正式提交，拒绝原因保持可见，不能靠归档会话或手动填满成果地图修饰通过。
8. **项目工作目录缺少源码。** 实际执行被派往只有工作资料的目录，多个 Agent 随后各自请求克隆代码，制造额外授权和分叉副本。工作目录必须在方向与执行上下文中可核对；代码任务需要明确源码位置和任务隔离策略。不能自动覆盖其他 Agent 已创建的代码修改。
9. **部分候选错误填槽并启动依赖。** 实机 Agent 显式返回空交付槽及缺失源码定位，兼容逻辑却将其映射到唯一槽。现在显式空数组保持空位，缺口阻塞依赖；同一要求和执行权下补充会追加续作事实。完整细节见 `partial-delivery-repair.md`。
10. **网络恢复被内部截止时间截断。** 源端连续 WebSocket 超时后会回退 HTTP，标题请求可能在回退前被 120 秒截止时间终止。对已受理且源端明确重试的同一次请求给予一次最多 60 秒连接宽限；出现真实文本增量或递增用量后，按最长 120 秒无进展判断超时。单纯状态通知、心跳、空增量、重复片段和重复用量不续期；持续输出不被旧固定总时长截断，也不重复发送。
11. **摘要被隐藏字节上限拒绝。** 真实项目的 29 条台帐及约 134 条事实已经达到 65 KB，叠加 JSON 契约后被 64 KB 检查拒绝为“契约无效”。移除此内部输入上限，完整授权资料交给用户源 Agent；源端上下文错误仍如实报告，不截断资料或伪造摘要。
12. **已导入任务阶段与旧阶段声明不一致。** 真实子任务阶段为“执行”，旧声明仍是“准备、整理、成稿”；详情页仅遍历声明阶段，出现“等我 2”却空列表。任务树改用声明与实际阶段的并集，并与源请求状态保持一致。任务行不再同时重复渲染两份执行进度。

13. **完整交付在重启后重新显示暂停。** 成果入库、源会话空闲和进程退出是不同事实。完整候选已经存在时，不能以重启后的源暂停状态重新要求用户回复；真正未完成、权限、失败仍需可处理。归档会话的旧拒绝记录不能重现为当前待办。
14. **前置成果更新后旧运行无恢复入口。** 旧设计运行固定了后来失效的部分成果。普通继续不能改变固定上下文，也不应跳过来源校验；需要明确的新受管尝试，检查停止回执和当前要求，重新固定有效前置成果，保留旧历史。
15. **摘要输出契约未约束引用范围。** 真实摘要请求产生了用量，但被语义重复关联校验拒绝。模型输出 schema 原先允许任意字符串，而领域要求当前输入中的根任务 ID。输出契约必须与后置校验一致，明确区分根任务 ID、子任务键及事实引用；不能通过丢弃错误条目或放宽归属校验掩盖失败。

16. **专注方向页的日程只有遮罩。** 旧布局的 `display:none` 覆盖已打开抽屉的状态。修复打开状态的明确布局规则，在普通与专注模式中验证轮盘、真实区间及关闭操作。
17. **手动摘要刷新留下延迟请求。** 手动点击后原 debounce 未取消，失败后可能再次派发同一版本。开始请求时消耗该项目已排计时器，失败留待明确重试，新事实版本按正常规则处理。

18. **子任务行继续展示旧命令。** 完整候选状态已就绪，但行内活动摘要回落到旧工具步骤。统一使用当前交付与请求投影，待验收、权限、失败分别展示；原始命令保留在执行详情，不占据任务摘要。运行中的全轮时长统一标为“本轮耗时”，不误称全部时间都在等待。

19. **中文路径图片无法预览，附件破坏正文排版。** 实际图片文件存在，但 Markdown 链接经过 URL 编码，后端直接拿编码字符串查找文件，报 ENOENT。同段多个链接又被替换成大块附件，标点独占段落。修复需统一路径解析、保留 realpath 目录边界与原始百分号，正文使用紧凑附件和真实缩略图；不能靠英文样例或放松路径授权掩盖失败。

## 3. 黑板、台帐与运行事实的边界

黑板和台帐是同一项目权威状态的不同视图，不能各自持有一份可独立修改的任务状态。当前源码已有可保留的基础：

| 边界 | 责任与源码证据 | 必须保持的约束 |
| --- | --- | --- |
| 领域状态 | `collaboration.ts` 的 `applyCollaboration` 接收命令；任务、规格、依赖、运行、提交、成果引用和事件保存在同一协作状态中 | 修改从领域命令进入，校验版本/归属/幂等；不能通过 UI 假完成 |
| 台帐 | `deriveLedger` 从协作状态生成任务、当前规格、运行和成果的逐项记录 | 能回答“谁按哪版需求做了什么，产物在哪里” |
| 黑板 | `deriveBlackboard` 基于同一台帐生成运行、评审、阻塞、就绪、完成视图 | 是状态投影，不新增独立完成率；具体授权和等待原因不可被粗状态吞掉 |
| 持久层 | `desktop/app/local-store.mjs` 保存版本化文档、不可变事实和 outbox；不可变事实有拒绝修改/删除的触发器 | 崩溃恢复、重试与回执不得重复创建任务或抹去历史 |
| 源 Agent 运行 | Session / Run / Attempt / SourceReference 保存实际源会话与请求 | UI 打开准确的叶执行；源回执证明工具状态，聊天描述不能替代回执 |
| 前端展示 | `projectActivity.ts`、任务树、进度、成果地图从项目状态推导 | 兼容粗粒度 `paused`，显示具体等待授权/回复/失败；不建立第三份真源 |
| 成果装配 | 计划输出位绑定任务与产物引用；已提交与已接受有区别 | 未完成保持空位；候选不伪装已核对；重试不得把过期产物覆盖当前版本 |

本次权限可见性修复没有改变台帐 schema，也没有把等待授权当作完成或普通暂停：它从当前执行关联的实际源请求推导可处理状态；历史、归档和取消会话不被旧请求复活。相同源会话只计一次，不同叶任务的请求分别展示。

## 4. QD-E2E-001：从真实需求到成果回写的完整用例

**场景：** 用户在新建项目输入一个需要查阅源码和多项修改的目标，附带截图；确认方向后，系统拆分成任务及子任务，自动执行独立分支，一条分支遇到权限请求。处理后从原运行继续，逐项装配成果地图，最后明确候选与已核对状态。

**前提：** 使用真实安装包和已配置的 Agent；先备份工作区；记录版本/提交。用独立项目或经授权恢复的真实项目执行，不手工改库制造通过。保留可撤销的代码工作树，禁止以删除用户任务清理失败。

| 步骤 | 操作与预期 | 必须留存的证据 | 基线 / 当前已知验证 |
| --- | --- | --- | --- |
| 01 进入与输入 | 从“新任务”粘贴文字和截图、上传附件；一次创建成功 | 原文、附件数量、可读缩略图、保存后仍存在 | 基线新建入口截图粘贴失败；修复后需实机执行 |
| 02 自动分拣 | 输出简短标题，完整需求作为正文保留；分类失败不能丢输入 | 标题与原文对照，失败时可继续操作 | 基线全文变标题；修复后需实机执行 |
| 03 定方向 | 项目和任务均有可见方向入口；显示目标、大纲、执行逻辑与输出物地图 | 小窗口和大窗口截图；大纲与输出位数据 | 基线有方向但布局损坏；修复后需实机执行 |
| 04 确认方向 | “满意/支持，请执行”或明确按钮都只确认当前版本一次 | 授权版本、领域事件、后续调度；重复点击不重复派发 | 基线出现认可后仍要求点击确认；修复后需实机执行 |
| 05 任务分解 | 根目标分解成多个任务，每项有子任务、依赖、负责人及验收；输出位事先可见 | 树结构、依赖和输出位绑定；无重复规划前缀 | 基线产生多个子任务；后续回包遗漏输出清单导致退化，需回归 |
| 06 多分支执行 | 就绪且独立的分支自动派发；依赖未完成不启动 | 至少两个不同执行/源会话引用，时间线和当前进度 | 基线启动两个子执行后被等待权限堵住，需实机验证继续推进 |
| 07 权限可见 | 分支 A 等待授权，立即显示问题、所属任务、查看授权入口；不被折叠/隐藏队列掩盖 | 顶部待处理列表与准确源会话；父任务计数 | 真实备份回放与新增回归：3 项授权 + 1 项回复均准确可见 |
| 08 非关联工作 | 分支 A 等待期间，分支 B、讨论和归纳仍可进行 | 新分支或讨论实际启动，不再报项目并发上限 | 基线连续拒绝；修复后需实机执行 |
| 09 原处恢复 | 对具体请求允许/拒绝，解释处理结果；不把用户回复发送到另一会话 | 请求 ID 匹配、回执、旧请求消失、原 attempt 延续 | 可见性回归保留准确 attempt/session；实际工具授权结果需实机验收 |
| 10 故障可处理 | 工具失败显示原因和继续/重试路径；失败不冒充运行或完成 | 失败原因与原运行引用；重试产生可追踪新 attempt | 新增回归覆盖失败原因；实机重试待验收 |
| 11 成果回写 | 每个完成子任务带真实文件/卡片/来源进入其对应输出位；未完成项留空 | 存在的文件、提交记录、来源版本、成果地图 | 基线 0 成果；真实完成链路仍需实机验收 |
| 12 自动汇总 | 输出到达后自动更新任务与项目成果地图；无需手工“拼成果” | 自动装配事件及结果，未完成格子的状态 | 必须验证实际输出，不以展示样例替代 |
| 13 候选与人工核对 | 源 Agent 的候选完成与用户核对分开，明确哪个版本被接受 | 提交/评审/接受事件，最新与过期标记 | 未完成验收时不得宣布全项目已完成 |
| 14 重启与重试 | 关闭重开恢复真实等待/成果；重复回执不重复任务/输出；过期运行不能覆盖新版本 | 重启前后引用一致；幂等和版本回归记录 | 领域测试可作为辅助，真实安装包恢复需补执行记录 |

**通过标准：** 01–14 实际完成并有证据才可称端到端通过。单个测试通过、Agent 发出“已完成”的文字、100% 动画或一个 HTML 预览均不代表整条流程通过。用户未核对的成果应明确为候选。

## 5. 本次可见性修复与已完成验证

变更位于 `projectActivity.ts`、`ExecutionRail.tsx`、`ProjectActivityRow.tsx`、`now-queue.css` 和 `tests/execution-progress.test.ts`：

- 从当前叶执行的实际源请求恢复等待授权/回复/失败；保留准确的执行和会话链接。
- “需要你处理”固定展示于侧栏执行列表上方；不受“当前关注”最多三项、隐藏排序或任务聚焦切换影响。多个独立请求均可找到。
- 显示所属任务及具体问题；错误单独计数。已归档、已取消、历史会话不会因旧请求复活。
- 项目状态、任务内进度和侧栏复用同一个项目活动投影。

验证证据：类型检查和生产前端构建通过；执行进度、当前关注队列回归通过；搜索摘要检查通过。对真实 SQLite 一致性备份进行只读投影回放，得到 3 项等待授权、1 项等待回复，均有准确源引用。该回放证明信息不再丢失，不等同于真实授权与工具恢复已经完成。全量测试及最终安装包检查以本任务 completion manifest 和集成验收记录为准。

| 多处独立状态拼接 | 任务行、Agent 卡、当前执行曾各读粗状态 | 复用 `deriveProjectActivity` 与执行展示投影；拒绝单独本地计时模拟百分比 |

| 重复确认入口 | 用户确认后会话仍要求“点击执行” | 单次确认当前版本，UI 和聊天走同一领域转换；重复确认无副作用，新版方向才需要重新授权 |
| 零散成果入口 | 用户要求项目与任务成果地图集中展示 | 汇总到对应范围；执行侧栏只处理工作和异常，不再放无关成果摘要；逐个入口核对后清退 |
| “查看任务与执行”冗余页 | 用户明确要求去掉单独中转页 | 直接进入当前任务树/方向/成果目标；保留旧链接兼容跳转，避免死链接 |
| 无来源的结果卡片 | 真实备份无成果，不能生成假完成卡填空 | 显示空输出位及未完成原因；真实结果到达再装配，不能拿 demo 卡回填 |
| 自动克隆多个源码副本 | 实际多个 Agent 因工作目录缺源码请求 clone | 明确一个项目源码锚点，每任务独立 worktree；保留已有修改。不要擅自清理用户或其他 Agent 的副本 |

此矩阵区分“已有隔离应保留”“本轮缺陷需修复”“后续结构调整”，不声称未执行的删除已经完成。

## 7. 项目体检与优先级路线图

| 优先级 | 健康判断 | 近期行动 | 验收门槛 |
| --- | --- | --- | --- |
| P0 可用性 | 权限入口消失、全局并发阻塞使项目停止；没有产物 | 本轮恢复真实等待可见、独立分支推进、明确执行口令转换；恢复实际项目 | QD-E2E-001 的 04、06–12 通过，真实成果入库 |
| P0 数据真实性 | 已有不可变事实和版本控制基础；输出位遗漏合并会破坏计划 | 保留方向/输出地图，校验旧回包与重复回执；完成来源可追踪 | 旧结果不得覆盖新规格；重启不丢等待和成果 |
| P1 需求入口 | 同一能力在不同输入入口表现不一致，长标题损害可读性 | 新建输入支持粘贴/附件，标题与原文分离，归纳失败仍可保存 | 真正的新任务入口多格式验收，原文可还原 |
| P1 信息架构 | 方向入口、状态、成果分散；大窗口布局失衡 | 可见方向文档和任务分解图，集中成果地图，收敛冗余跳转 | 小/大窗口无挤压或遮挡；每个输出位有清晰归属 |
| P1 执行环境 | 资料目录与代码目录混用引发重复克隆和授权 | 项目明确源码锚点、工作区就绪检测、每任务独立 worktree | 派发前能核对目录；多个任务不修改同一分支 |
| P2 模块维护 | 样例/真实数据源共文件、CSS 跨层覆盖、输入逻辑重复 | 拆分数据源、整理样式归属、共享输入附件处理；增加结构契约测试 | 行为不变且测试通过，不删除真实历史或有用 fixture |
| P2 发布质量 | 仅构建/单元测试无法发现真实用户入口失效 | 每次发布固定跑该 E2E 的权限等待与原处恢复路径 | 安装包版本、远端 SHA、实际运行和成果回写证据齐全 |

当前最重要的质量目标是让一个真实目标可靠地走完“确认方向 → 自动分解执行 → 可处理等待 → 成果回写”。代码覆盖率、卡片数量和新增页面不能替代这一结果。
