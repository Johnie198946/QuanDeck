# 授权、真实进展与项目规范：实际流程审计

基线为 QuanDeck 0.11.1（70c74ae114b70ecb1061f594196b19a6177334ac）。本文件区分产品现状、修复设计与验收证据，不能把方案当成已完成。

## 授权为何频繁

旧适配层将源 Agent 的多种授权响应压缩成“允许本次/拒绝”，Codex 线程和回合还固定传入 on-request，线程沙箱固定 workspace-write。每个执行任务可以建立新的源会话，当前会话授权不能当作全项目永久授权。与直接使用 Codex 的会话、规则和配置不同，授权体验因此不同。

修复遵循源协议：展示请求实际提供的单次、当前会话、命令规则或网络规则选项，并清楚说明生效范围；选择必须来自当前待请求，过期/伪造选项不能生效。不建立 QuanDeck 的隐式自动允许表，不替源 Agent 放宽安全判断。

方案取舍、执行范围授权、工具访问许可与成果验收分别处理。常规实现细节不重复询问；方向确认只绑定相应版本。源端工具权限不是“是否满意方案”。

## 运行层的职责

QuanDeck 确实维护本地适配与协作编排层：启动/连接源会话、转发协议、接收事件、记录当前运行、派发就绪任务、回收成果。模型推理、实际工具调用、沙箱与工具审批仍由源 Agent 执行。

需要审视的是边界，而不只是文件名 runtime：连接恢复不能重复派发；本地超时不能冒充源任务完成；用户权限响应不能被适配层削减；编排不能另存一套与台帐矛盾的完成状态。所有页面须从同一协作事实派生。

## 可持续观察的进展

任务展示由“已完成/总数”拓展为方向、执行、交付、验收的证据轨迹，同时显示当前行动、已推进事项、待补齐事项和最近活动。轨迹只投影已有方向版本、运行事件、检查点和提交；未知总工作量不伪造百分比，等待授权不伪装工作中，候选不等于验收完成。

主列表保持紧凑，详细活动按需展开；窄窗口纵向阅读，宽窗口清楚显示阶段关系。进展组件共享派生逻辑，避免任务列表、任务详情、总览各算一份状态。

## 三种 Spec 身份

任务规格记录“这一项工作按哪版要求、产出什么、如何验收”。任务交付中的设计说明文件是候选产物，不能因名称含 spec 自动成为权威项目规范。项目规范则是明确纳入并发布的统一版本。

现有台帐已经关联任务规格、运行和产物；已有整合机制保存不可变章节版本与来源。待补齐的关系是：项目规范标识、来源任务与产物、任务继承的规范版本、执行固定的规范内容，以及更新后受影响任务的过期提示。规范复用现有版本化整合，不建立第三份独立真源。

成果地图持续自动装配。把候选提升为项目规范属于明确的规范发布，不应把所有普通成果汇总都变成手动点击。

## 验收状态

已在安装版创建独立验收项目，经真实 Codex 返回方向正文、3个主任务、4个子任务与5个输出槽；仅确认方向后未启动业务执行。后续完整实机结果见下文。源模型曾连接重试后恢复。发现已采纳方向仍在侧栏列为等待回复，以及返回主窗口时交接弹窗未关闭，纳入本次修复。确定性回归不替代原生真实 Agent 验收。

## 自动执行前的账户检查与恢复

真实验收发现：协议握手成功后，可选 account/read 异常曾被当作登录失败，导致下一个依赖任务未被源端受理。账户检查的非认证异常现记为 unknown，保留脱敏诊断；实际模型调用仍由源 Agent 鉴权。明确未登录或认证失败继续阻止执行，不把未知状态伪装为已登录。前置检查拒绝与源端已接收必须分别呈现，并保留显式恢复路径，避免打开不存在的源会话。

## 候选安装后的真实验收

第一轮候选安装后，原先显示 JSON 的子任务方向已恢复为摘要和完整正文；确认成功，三主四子身份保持，未新增重复任务。项目自动执行开启后，两个内容叶任务并行运行并分别提交候选。已确认的子任务新增要求进入实际执行上下文，也出现在交付内容中。之后示例任务被受理前账户检查误挡，已定位并继续修复；未把这次部分运行标成完整 E2E 成功。

用户原页面重构执行已恢复并提交开发与构建验证候选。正式产品已单独整合缺少的正文草稿/最近确认快照切换、讨论栏收放和窄屏模态抽屉，保留已有业务操作；独立原型没有整树复制进当前仓库。正文快照只读，历史模型仅保留最近确认版本，没有虚构完整历史。

## 真实执行链已完成交付

第二轮安装后，明确未受理的叶任务出现安全重派入口。原失败记录保留，重派获得真实源端受理；独立分支继续执行。四个叶任务、两个章节任务和一个最终整合任务依次交付，五个计划输出槽全部自动填入候选成果，无须手动点“汇总”。实际生成项目规范、两个独立章节、合并 Markdown 与 HTML 文件。任务讨论新增的等待授权与等待补充区分进入后续正文；未完成项示例的交付、验收单元格仍为空。此时七项候选交付不等于七项已人工验收；后续实际核对另记如下。

实机发现并继续补齐两处阅读与核对缺口：实时快照使 Markdown 内附件组件重挂载，导致打开的预览闪退；成果地图缺少直接核对当前候选的入口。另修正重试已被受理后仍把旧失败计入当前异常，以及首次候选误显示“已被其他成果版本替代”。旧失败、候选与规范历史均保留，不通过改写历史掩盖问题。

## 规范正文与文件的边界

原设计说明附件已作为任务成果登记并被下游引用，但此前没有项目规范发布记录，不能据此声称附件全文已成为统一规范。现在规范仍复用台帐中的整合版本：来源成果通过验收后，可读取同项目 Markdown/文本附件全文，保存原件 SHA-256 与导入回执，再核对发布。黑板引用规范版本、hash 与事件水位；下游运行固定完整正文和来源，已经开始的上下文不静默换版。

当前规范正文导入仅支持桌面端 UTF-8 .md/.txt、300000 字节与100000字符以内。普通图片、PDF、Word等附件预览不等于这些格式已支持规范正文导入。附件后续变化也不会绕过版本发布直接更改规范。


## 实机验收、规范发布与真实复用

第三轮安装后，打开真实 HTML 附件并跨越连续快照更新，预览保持打开和可滚动。成果地图新增就地核对：逐项标准与核对说明绑定当前候选版本，不默认勾选。先核对最终整合时，台帐因前置任务未验收而拒绝；依次核对四个子任务、两个章节和最终整合后，五个输出槽显示全部已认可。用户业务项目的候选没有被本次验收代为认可。

随后在应用中选取已认可的说明册成果，原生读取 Markdown 附件全文，保留原件指纹与导入回执。草案含统一规则说明和原始附件全文两个章节；发布为项目规范 v1。只读数据库核对规范内容哈希、两章全文、来源回执与黑板指针一致。原附件中的“候选”等历史措辞保留，治理说明明确其原交付时点，实际认可与发布状态以台帐事件为准。

再次通过“新任务”直接创建规范继承核对任务并委派，没有强制进入讨论。真实源 Agent 回答引用已发布 v1、同一版本指纹及两条约束。固定上下文与实际源请求均包含规范完整正文、附件原件指纹和导入身份，证明后续执行实际复用，而不是仅在界面显示版本号。此次新增任务的交付与原七项工作分别记录。

## 发布验收边界

代码集成执行类型检查、领域测试、Node 协议测试与生产构建；原生完整流程和只读台帐验证独立记录。公开仓库与 PRD 只记录脱敏结论，真实数据库、完整源请求、屏幕记录及本机凭证不上传。

普通成果自动装配不要求用户手动拼接；正式认可、项目规范发布与工具权限仍各自有明确含义。源会话授权不会自动升级为所有未来任务的永久权限；当前规范全文导入不包含 PDF/Word OCR。旧项目和其他任务工作树保留，不以无差别合并或清空数据宣称全部历史工作完成。

实机追加修复：直接创建的普通任务没有预声明输出槽，交付仍合法记录在同一台帐。进展轨迹必须同时计入这些交付；源会话在完成一轮后的闲置等待，不能盖过已经入库的候选状态。真实追问、工具授权、失败与未解决事件保留优先处理。

最终组合校验：完整领域回归、291 项 Node 协议测试、TypeScript、生产构建以及 38 项发布门禁通过。原生安装验证与远端双平台安装包结果见同版本 Release verification.json。
