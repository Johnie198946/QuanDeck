# 将成果附件纳入项目规范

已验收成果的附件必须先读取正文、由用户核对并发布，才成为项目规范。文件名、链接、上传、读取成功都不表示规范已生效。

## 用户路径

1. 在成果地图的「项目规范」选择已验收来源，创建规范修订草案。
2. 「从成果附件读取正文」列出来源成果已登记的 `.md` / `.txt` 附件，以及来源正文中明确链接的本地文本文件。
3. 点击「读取附件正文」，显示完整正文和导入指纹；确认后「加入规范草案」。正文可以继续编辑，导入原件记录保持不变。
4. 保存正文，核对正文、来源及后续影响，发布项目规范版本。普通成果汇总不会代替规范发布。
5. 后续任务固定已发布版本，接收完整规范正文及文件名称、原文件 SHA-256、导入 ID、成果关联、相对路径或附件 ID。原文件之后发生变化不会改写规范；需要重新导入并发布修订。

## 唯一真源与来源链

沿用 `integration` 的版本、修订和事件台帐。`attachmentImports` 保存主进程读取的不可变原件正文、字节 SHA-256、文本 hash、文件身份、来源成果及导入时间；章节的 `attachmentSources` 固定这些来源。服务端保存章节时校验原件回执，不能由页面伪造指纹或跨来源引用。正文经用户修改时，章节版本固定修改后的内容，原文件指纹仍明确指向导入原件。

台帐导出的 JSON 包含整合版本、章节和原件回执；Markdown 展示当前生效正文、来源指纹和规范历史；黑板显示当前规范版本及规范/整合事件水位。候选、草案与已发布版本保持分离。

## 本机边界与失败处理

- 桌面专用 IPC 只接收项目 ID、已验收成果 ID、该成果内的附件候选 ID，不接收任意路径或正文。
- 文件来自同一项目已绑定的来源执行目录，或同一已验收成果登记的附件存储。读取后在原子写入时再次核对来源验收状态。
- 真实路径必须留在来源项目内；拒绝目录越界、指向项目外的符号链接、网络 URL、网络共享路径及非普通文件。读取过程中文件身份、大小或时间发生改变则拒绝。
- 仅支持 `.md` / `.txt`，最多 300000 字节、100000 字符。UTF-8 错误、空文件、NUL 字符、大小不符、文件缺失均显示错误，不截断正文继续发布。
- 不执行文件内容、不抓取网络，也不自动把链接提升为规范。浏览器模式提示使用桌面客户端读取本地文件。
- 路径识别覆盖内联 Markdown 链接和结构化回复附件。其他 Markdown 引用形式仍按普通正文保留，可先在成果中添加明确的本地附件链接。

## 验证

`tests/spec-attachments.test.ts` 覆盖真实本地读取、不可变回执、核对发布、完整上下文和台帐导出，以及越界、符号链接、UTF-8、大小、指纹篡改、来源变化等失败边界。

`tests/spec-attachments.browser.mjs` 使用临时 Markdown、隔离存储与实际本机读取模块，验证正文预览、保存与发布、后续任务继承及 320 / 768 / 1440 / 1920 宽度，不调用模型或接触用户项目库。运行前先构建 `desktop/build-core.mjs` 并启动独立 Vite 实例。
