# 任务记忆与交接：后端约束设计

## 目标与边界

新任务或已有但尚未执行的主任务，可以选择一个已验收任务作为前置，使用其固定成果和交接记录，在新源会话执行。AI 可以阅读、规划、开发和提供总结正文；任务身份、引用关系、版本、状态、入库、接续和汇总必须由后端决定。提示词是内容指引，不是安全或一致性边界。

项目事实仍在现有项目协作台帐。共享黑板是台帐的当前工作投影，Markdown 台帐、黑板文件和搜索索引也是后端生成的投影，不是第二份可编辑真源。源 Agent 负责模型推理和工具调用；QuanDeck 负责业务状态、协议适配、版本和事务，不建立另一个模型执行引擎。

## 分阶段约束

| 阶段 | AI 的工作 | 后端强制动作与拒绝条件 |
|---|---|---|
| 新建 | 可辅助理解目标 | 创建任务 ID、任务要求和验收条件；普通新建不强制打开讨论；引用交接时原子创建依赖与固定来源回执，重复请求返回同一任务 |
| 查阅 | 可展开资料、归纳要点 | 派发前生成固定 context：当前任务要求、规范版本及正文、项目全量未归档任务记忆索引、必需前置成果、结构化交接；来源不完整、过期、哈希不符或引用版本变化则拒绝 |
| 做方案 | 基于固定规范和任务范围提供方案内容 | 方向版本和确认独立记录；确认只对相应版本有效；方案讨论不冒充业务执行，不将一般讨论措辞提升为用户授权 |
| 开发 | 在本任务范围内执行、提供检查点 | 后端先提交 claim/context，再启动源会话；新运行不能带旧 sourceSessionId 续接另一个任务；回执必须绑定当前项目、连接、任务、运行及执行代次 |
| 录入 | 提供成果与可选结构化交接内容 | 严格解析结果，拒绝伪造身份/状态字段；检查 run/spec/context/来源；同一事务追加 artifact、submission、handoff 和事件，持久化失败全部回滚 |
| 总结 | 提供 summary/completed/decisions/remaining/nextSteps 的正文 | 后端分配记录身份、来源、序号和哈希并写入固定 schema；未提供字段时生成标明 derived 的确定性摘要，不伪称 AI 已详细总结；畸形输入不静默收纳 |
| 交接 | 可提出下一步建议 | 建立来源任务 → 接收任务的强前置关系；接手者由实际 claim/运行事实确定；“建议下一步”不会自己成为新任务或已授权执行 |
| 验收与合并 | 可提供候选和复核内容 | 完成状态来自验收记录或已明确授权的既有规则；地图依据交付槽自动归位，缺失留空，候选与已认可分开；发布项目规范是单独版本动作 |

“已送入固定上下文”可由代码和回执证明；“模型已逐字阅读、理解并完全遵守”不能由提示词或一个阅读回执证明。需要以产出、验收标准及来源核对判断内容质量。

## 固定格式的任务总结

每次成功提交都有一条不可变 `TaskHandoff`，与同次 submission/artifact 一一对应。

- 内容：摘要、已完成、工作决策、遗留问题、下一步。工作决策只是交接说明，不升级为用户确认条件。
- 身份：项目、任务/子任务、提交、成果、运行、上下文、任务要求版本和项目规范版本。
- 来源：成果正文哈希、前置 artifact/version/hash、context hash；内容哈希和完整记录哈希分开。
- 治理：schema、后端记录时间/序号、可信 actor、内容来源 provided/derived。
- 当前状态：当前/被替代、候选/已验收/需修改、失效与接手情况由 reviews、任务状态和 runs 派生，不改写历史总结。

旧任务缺少结构化记录时，只生成明确标记 `legacy-derived` 的历史投影，不补造当时并不存在的提交记录。后续新提交使用新 schema。

SQLite `immutable_facts` 对交接记录与交接来源回执执行与规范版本相同的保护：不能修改、移除或复用同一 ID 写入其他内容。项目快照与不可变索引在同一个 SQLite 事务中提交；索引是完整性保护，不是另一份业务真源。

## 从已有任务交给新任务

“使用此任务交接”选择同项目当前有效的已验收成果，目标可选新建或已有未开始的主任务。后端保存 `TaskHandoffTransfer`，固定来源任务、交接 ID/hash、成果 ID/hash、验收 ID、接收任务、请求幂等键和指纹。不会把源任务会话附到新任务。

新任务派发再次核对固定来源。如果源已重开、失效或变成另一版成果，返回 `HANDOFF_SOURCE_CHANGED` 或相应来源错误；不能自动把另一版当成用户原先选中的来源。重新选择应留下新的明确操作，不篡改已发生的运行。

创建默认不执行，可选择“创建后立即执行”。先持久化创建，再走正常派发；派发失败仍保留已创建任务。并发点击和网络重试不生成重复任务，也不重发已受理或受理结果未知的执行。

“21E → 14D”这样的短号只有在当前项目中能唯一定位时才可以直接使用；重名或歧义不能由模型猜测。界面使用真实任务选择与后端键绑定。入口既支持创建新接收任务，也支持已有、尚未执行的主任务。已有目标的标题、任务要求、方案和验收条件保留；用任务版本 CAS 防止并发编辑冲突，已经执行、提交或正在运行的目标不可重新绑定。

## 一个任务与源会话

不同任务不得共享一个受管理的源会话。新执行调用必须申请新源会话；服务端同样拒绝跨任务 adopt、普通 run 传入旧会话，以及源工具返回已占用会话的情况。源会话身份按 provider/connection/sourceSessionId 确定，不能只比较一个无作用域的字符串。

同任务的讨论、执行、失败后的新尝试可能有多条历史记录，均属于同一个任务。恢复同一次已受理运行可使用原会话，必须核对所有权；修订或失效后生成的新运行使用新会话。历史与当前运行分开，不以“一个任务永远只能有一个聊天 ID”阻断正常恢复。

## 界面

任务详情显示“任务记忆与交接”：摘要和完成/遗留/下一步按固定字段阅读，来源与版本可展开。来源任务显示已交给哪些任务、是否实际接手；目标任务显示接收自谁和固定的来源。历史搜索中的已验收任务提供“交给新任务”，候选与失效来源说明不能作为强前置的原因。

规范正文仍在成果地图的规范入口，普通成果仍在项目/任务成果地图，交接面板只显示记忆与来源，不复制一个成果中心。

## 验收矩阵

1. 提交成功有且只有一条交接；重放幂等；伪造 actor、状态、ID/hash、缺失运行绑定均不能越权入库。
2. 历史交接/转交回执改写或移除被 SQLite 拒绝，事务整体回滚；旧数据可读取。
3. 新任务完整固定前置和总结，短摘要不能代替必需全文；来源变更后不静默换版。
4. 正常新运行、重复源端回执、跨任务 adopt、未知受理恢复覆盖正反例；不发送到别的任务旧会话。
5. 原生 E2E 从新项目、方向讨论、任务细化、任务方案、实际执行、交接复用到成果自动汇总；UI 观察和只读台帐证据互相核对。

实际测试与发布证据记录在本任务 completion manifest；本设计文档本身不代表已完成实机验收。
