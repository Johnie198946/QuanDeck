# 方向讨论范围与空拆分修复

2026-11-17 的真实端到端验收发现：项目已拆为三个主任务、四个子任务，进入其中一个子任务讨论时，Agent 又返回了全项目拆分；子任务方向页的“目标”为空。后来 Agent 明确返回 `tasks: []` 撤回多余拆分，控制台能展示摘要，主方向页却把协议 JSON 当成摘要。

根因与修复：

- 原来每个讨论都注入“项目需要多个业务主任务”的同一模板。现在区分项目、任务、子任务和章节；项目仍可拆多主任务，任务只细化自身，具体子任务可以直接执行而无需再拆，章节不创建任务。
- 讨论简报从既有台帐的当前 spec revision 带入目标和验收标准；只补充真正阻塞的缺失条件，不强制多轮澄清。已有下级工作列为只读背景，避免再创建。
- 子任务方向创建曾使用空目标骨架。现在从实际任务要求初始化目标和验收标准，旧未采用的空骨架也会补齐；不改用户内容或已采用方向。
- 接收层识别明确重复当前任务、祖先或兄弟名称的越界结构，保留原始回复和说明，但不将越界拆分导入。章节拆分同样拒绝导入；这不是对自由文字的语义推断。
- `tasks` 省略表示该字段未改变；`tasks: []` 表示撤回本范围尚未生成的拆分草稿。生成逻辑遇到空数组会停止，不再回捞旧轮非空列表。此动作不删除已生成的项目任务、子任务、计划版本或成果。
- 运行时与显示层都支持协议标签、裸 JSON 和 JSON 代码围栏；合法空 tasks 不再令 summary/outline 丢失。未采用的旧错误结论会从保留的完整公共回复恢复结构，原会话消息仍保存原文。

验证包括三个主任务、四个子任务的实际形状；子任务目标与验收继承；项目/子任务/章节范围；越界回传拒绝；空数组撤回；方向正文仍可确认；已生成台帐 ID 不变；用户编辑及已采用文档保护。真实出错回复和项目快照只读复制后也完成恢复验证，没有修改真实数据库或调用模型。

## 已生成任务的空拆分修订

已存在任务图时，确认 `tasks:[]` 只撤回待生成的拆分草稿。台帐追加一个 `retainedFromVersion` 指向旧图的新版本，关联本次已确认方向；既有任务键、层级、依赖和输出槽 ID 保持稳定。旧图、提交正文、附件及输出绑定不被删除。旧版本里已经出现“方向已确认、任务图还在上一版”的状态，在规范化时追加同样的继承事实恢复，重复加载不重复追加。

本次方向正文如果引入新的约束，仍按原有台帐规则更新任务要求并提示重新核对；不能用“保留任务图”将旧候选虚报为适用新要求。新图固定事务内最终的任务要求版本。自动执行需明确开启当前方向；在图身份不变的继承链中，未确认受理的调度回执始终保留，避免重派。只有要求版本确实改变的已确认执行才允许按新要求重新安排，未改变的执行沿用原回执。

验收：项目与任务两种范围，已有候选、空拆分确认、稳定输出槽、旧事实不可变、当前要求版本一致、重新开启成功、未知受理继续暂停，以及历史恢复/重复确认的幂等性。
