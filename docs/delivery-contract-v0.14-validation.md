## 原生完整流程

通过 QuanDeck 原生界面新建独立项目，使用已配置的 Codex Agent。没有直接修改真实数据库，没有使用模拟回复替代业务执行。

1. 创建项目，讨论并确认项目方向和两件最终交付清单。
2. 讨论任务 A 的执行方案；任务范围、交付条件和版本进入固定上下文。
3. 一次启动自动执行，依次形成子任务、任务 A、任务 B 和两个最终整合节点，共五个不同的执行来源会话。
4. 逐件检查候选正文与实际文件；任务贡献填入任务地图，最终 Markdown 和 HTML 填入项目地图。
5. 发布子任务成果 v1、项目总成果 v1；已验收规范内容自动进入 Spec 草案，再明确发布 Spec v1。
6. 在原生沉浸阅读与历史版本中打开 HTML、Markdown；最终界面显示必需件 2/2 已验收、0 缺项、0 待更新，项目成果和项目规范均为 v1。

执行与最终候选生成由系统自动推进；内容验收和正式发布由测试操作者完成。未声称 AI 自行认可质量，也未把模拟安装烟测当作真实 Agent 全流程。

## 实测发现并修复

- 首次 Spec v1 建立基线曾把同批已有效验收的下游 HTML 误标为过期。后端现在只保留验收、要求、收据和来源仍匹配的既有成果；候选和执行中任务不适用此例外，Spec v2 的真实变更仍需重新核对。
- 兼容恢复只追加一次恢复事实，不重写三个已发布版本、不重新生成文件、不产生第六次执行。
- 单文件相同任务/文件条件曾重复显示。现在一个勾选映射到两个独立后端索引，取消勾选同步撤销；多个交付件仍分别核对。
- 方向页交付范围、讨论的契约固定、任务目录混入规划条目及安装烟测旧断言已修复。
