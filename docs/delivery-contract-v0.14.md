# QuanDeck 交付清单、成果合并与规范维护

日期：2026-11-17。状态：V0.14.0 已公开预发布，原生流程和双平台安装验收通过。完整证据见 [验收与发布记录](delivery-contract-v0.14-validation.md) 和本次 completion manifest。发布源码固定为 `b25daea3322eae94629a1e7b30ff27252fa82fba`；后续文档归档不改变安装包。

## 目标

项目方向确认后，后端建立版本化交付清单、任务与子任务依赖以及最终整合职责。任务逐件提交、逐件校验、逐件验收，最终成果自动填入项目地图。用户明确核对后发布不可变版本。AI 可以拟定内容，不能自行登记验收、发布或改写项目真源。

## 完整执行流程与职责

1. **查阅与定方向**：后端从台帐固定项目 Spec、任务要求、已验收来源与交接；AI 读取这些固定内容，提供大纲、执行逻辑、候选任务和候选交付清单。
2. **确认并细化**：方向确认命令校验版本，保存任务/子任务、依赖及交付契约。后端为每件项目最终成果创建整合责任，依赖图循环或责任缺失不能被静默接受。
3. **任务讨论与执行**：一个任务绑定独立来源会话；任务讨论固定自己的交付契约。确认方向后，已授权的调度器按依赖推进；讨论回传不能替代执行结果。
4. **提交与登记**：AI 只提供内容、文件路径、交付件标识、总结和交接内容。后端读取实际文件，校验身份/版本/来源/逐件覆盖，再原子登记成果、收据、总结及交接。
5. **逐件核对**：候选产生后即可供依赖任务生成下一版候选；内容的人工验收是独立事实，不能由“Agent 已完成”代替。缺失、过期、错误文件和未核对条件会阻止有效验收与正式发布。
6. **自动合并**：调度器启动各个最终整合任务。每件最终成果拥有独立责任、输入来源和收据；已完成的位置显示内容，未完成的位置保留空位和原因。
7. **正式发布及规范维护**：后端从当前有效已验收项冻结发布快照；规范类产出自动形成 Spec 草案，人工明确发布后产生正式规范版本。地图、黑板、任务记忆均从这些事实重建。

代码验证结构、身份、文件、版本和状态转换；内容是否准确、设计是否满意仍需要验收者核对。自动生成最终候选不等于自动代用户确认质量或正式发布。

## 两层成果地图

项目地图只展示项目最终交付清单，例如完整攻略、预算表、出行资料包；任务地图展示对应任务及其子任务的中间产出，例如酒店比较、路线核验。每个最终交付件可引用多个任务贡献，同一任务可交付多件不同格式的成果。点击贡献可下钻，不在项目地图重复铺开所有中间产出。

空白任务地图提供“定义交付清单”入口，不强制开启聊天。清单每件至少有稳定标识、名称、责任任务、格式、必需/可选、独立验收条件及契约版本。地图显示等待、执行中、候选、需修改、已验收、需更新和正式发布版本；候选填满不等于正式完成。

## 硬约束与数据归属

| 数据 | 唯一写入位置与责任 |
| --- | --- |
| 交付定义、版本、责任绑定、变更理由 | 台帐中的 goalPlans；后端命令校验后原子写入 |
| 内容、不可变文件副本、来源、逐件收据 | collaboration artifacts/submissions；本机可信读取边界计算文件哈希 |
| 验收、交接、依赖、执行事实 | collaboration；后端校验后追加事实 |
| 合并草案、发布版本、项目 Spec | integration；版本与引用不可变 |
| 黑板、成果地图、记忆索引 | 从上述事实计算的投影，不能建立第二套可编辑真源 |

任务级验收条件与逐件条件分别保存、同时校验。新增或修改交付件不会删除原任务的验收要求；人工记录完成同样必须逐项核对当前任务版本和每件收据。

模型文本中的“完成”“已发布”“已校验”不触发业务状态变化。模型只能提交内容及槽位标识；后端验证当前任务身份、固定上下文、契约版本、来源有效性、实际正文/文件和必需项覆盖，才生成收据。文件内容由本机读取、格式检查、哈希并冻结到附件库，禁止模型提供可信哈希。文件路径必须位于当前执行绑定的项目目录内，拒绝越界、符号链接逃逸、读取时变化、空文件及不匹配格式。

## 自动整合与正式发布

新项目使用严格交付契约。每个项目最终交付件由后端建立独立系统整合任务，引用贡献任务及其固定成果版本。依赖未满足时等待；满足授权与依赖条件后由现有调度器启动。重启、重复回执和结果重试保持幂等；受理状态未知时不重复派发。系统整合任务不能依赖自身，不能由 AI 省略最终合并环节。

生成最终内容与正式发布分开：系统可自动生成候选，只有当前必需项全部通过逐件验收且来源仍有效时，发布入口才可用。发布请求携带预览指纹；后端重新检查，防止预览后清单或来源变化。一次发布冻结整份清单及每件来源，保留历史发布版本。可选项的缺失明确显示，不假装已经产出。

## 交付清单变更

支持新增、修改、取消、替换、拆分、合并。所有变更必须有理由、基线版本和幂等标识，先显示预览：哪些槽位变化、哪些任务受影响、哪些旧成果需要更新。确认应用后产生新版本，保留原定义与已发布历史；不删除历史证据。并发版本不一致时拒绝覆盖，要求刷新。仅修改内容契约的槽位递增契约 revision；未受影响的收据继续有效。取消项目终件会取消其后续整合职责，历史版本可追溯。交付改版使受影响的旧授权与候选失效；若来源执行尚未真实停止，后端保留待更新状态。取得真实停止回执后，才更新执行版本与领取编号并恢复可调度状态；未知受理或未知外部动作不能被本地“取消”掩盖。

## 缺项与错误恢复

| 情况 | 后端处理 |
| --- | --- |
| 无结构化结果、缺必需件、错误槽位或契约版本 | 不完成任务，显示具体缺项；仅在已有自动执行授权内允许有限补交 |
| 文件不存在、格式不符、越界或读取变化 | 拒绝该次有效交付，不生成可信收据 |
| 任务或固定上下文身份错误 | 拒绝提交，不能靠改写 prompt 放行 |
| 来源更新、验收撤销或交付定义变化 | 关联候选标记需更新，禁止用旧来源正式发布 |
| 重复请求 | 成功提交重放原冻结文件与回执，不重新读取可能变动的源文件；同键不同内容拒绝，不重复写台帐或启动任务 |
| 受理结果未知 | 保留未知状态并核对，禁止盲目重发 |

## 项目规范维护

契约明确标记 purpose=project_spec 的规范产出，在验收后自动纳入项目 Spec 草案；不能仅凭文件名含 spec 就获得规范地位。后端建立来源关系、草案版本和维护状态，AI 只提供正文。已发布 Spec 保持不可变，新内容形成新草案，明确核对发布后才成为后续任务固定上下文的规范版本。

自动维护不覆盖人工已编辑章节；存在冲突时保留两版并要求解决。所有冲突明确选择后，后端一次性建立新草案版本及来源归因；未解决阶段不把旧人工正文错误归因给新来源。黑板显示已发布 Spec 引用、待维护草案及来源变化；不保存另一份可独立改写的规范正文。交付物变更和规范变更保留来源链，后续任务读取同一项目规范与相应固定交接。

首次发布 Spec v1 是建立基线，不追溯撤销发布前已有效验收、要求与收据仍匹配的成果；候选、仍在执行的任务和伪造完成标记不享有这一例外。后续 Spec v2 仍按来源变化重新核对。旧版本误标产生的状态仅在验收、来源、契约和输入指纹全部保持一致时由后端重建，并追加恢复事件；不改历史、不降低版本、不重新派发。

## 前端交互

方向方案页从台帐直接展示本任务已登记的交付清单，子任务清单与项目最终件各归其范围；未采纳讨论建议单独呈现。任务讨论固定目标任务的实际清单与契约版本，启动后清单改变时拒绝旧讨论回传，要求更新上下文。

成果地图采用“章节清单 + 当前成果正文”，项目地图提供任务贡献下钻；窄窗口切换为单列，操作不溢出。清单编辑默认收起，点击展开；变更预览先说明影响再应用。逐件验收展示每件内容及独立条件，缺收据不能验收。只有单个交付件时，完全相同的任务条件与该件条件合并为一个勾选，明确显示对应文件，同时映射到后端两套记录；多文件仍须分别核对。发布面板列出必需/可选项及阻塞原因，用户一次核对后发布。高层界面不要求用户理解 hash 或内部 runtime 字段，详细来源在溯源处展开。

## 兼容与验证

旧项目不静默升级为新严格契约，不自动派发新整合任务；历史结果仍可读。新建项目和明确采用新清单使用 contractSchema=1。验证包括域测试、后端命令/IPC、真实文件校验、幂等并发、任务与项目地图范围、320–1440 像素布局，以及原生 App 从创建项目到多件最终成果发布的完整流程。未通过的环节必须保留明确阻塞状态，不得以模拟结果冒充真实验收。
